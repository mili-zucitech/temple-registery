--------------------------------------------------------------------------------
INCONSISTENCY-01
Issue: Employee status representation conflict
Files: 04_schema_design/04_employee_schema.txt vs PDF R3.4.1h
Description:
  The employees table uses deleted_at (soft delete) and date_of_leaving
  (departure proxy) to represent employment state. The PDF requires three
  explicit status values: Active, On Leave, Retired.
  "On Leave" has no representation in the current schema. An employee on
  leave would falsely appear as "Active" (no date_of_leaving, no deleted_at).
  "Retired" employees have date_of_leaving set but no semantic distinction
  from resigned employees.
Impact:
  DC viewing staff list cannot distinguish active from on-leave employees.
  Any staff module built on current schema contradicts PDF requirements at
  the data layer.
Fix files:
  04_schema_design/04_employee_schema.txt -- add employment_status ENUM
  05_workflows_and_states/00_state_machines.txt -- add employee status transitions
  08_api_planning/00_api_endpoint_registry.txt -- update PUT /employees/{id}
    to accept employment_status field

--------------------------------------------------------------------------------
INCONSISTENCY-02
Issue: DC declaration review actions mismatch
Files: 05_workflows_and_states/00_state_machines.txt vs PDF §3.5.3 step 2
Description:
  The asset declaration state machine defines 3 DC actions:
    APPROVED, CLARIFICATION_REQUESTED, REJECTED
  The PDF defines 3 DC actions:
    accept, query, flag for physical verification
  REJECTED (docs) is not the same as "flag for physical verification" (PDF).
  A rejection implies the declaration is refused. Physical verification flag
  means the DC needs to physically visit and verify, then continue the
  process. These have different downstream actions.
Impact:
  DCs cannot flag a declaration for physical verification. This action is
  mentioned explicitly in the PDF as a DC capability and is a compliance
  requirement for on-the-ground verification workflows.
Fix files:
  05_workflows_and_states/00_state_machines.txt
  04_schema_design/06_asset_declaration_schema.txt (add PHYSICAL_VERIFICATION_REQUESTED to ENUM)
  08_api_planning/00_api_endpoint_registry.txt (add flag endpoint)
  07_dashboards_and_reports/00_dc_dashboard.txt (DC action buttons)

--------------------------------------------------------------------------------
INCONSISTENCY-03
Issue: Dashboard status label vs state machine naming
Files: 07_dashboards_and_reports/01_temple_authority_dashboard.txt
       vs 05_workflows_and_states/00_state_machines.txt
       vs PDF §4.4
Description:
  PDF requires dashboard display labels: Not Started, In Progress, Submitted,
  Approved, Rejected.
  State machine defines internal states: DRAFT, PENDING_REVIEW, APPROVED,
  REJECTED (or CLARIFICATION_REQUESTED), SUPERSEDED.
  There is no documented mapping between these two layers.
  DRAFT maps to "In Progress" or "Not Started" depending on context.
  A temple with no declaration record at all is "Not Started" (no row in DB).
  A temple with a DRAFT declaration is arguably "In Progress".
  Without this mapping, frontend engineers will make independent choices
  that may not match user expectations.
Impact:
  Inconsistent display labels across dashboard and module status cards.
