3. CONTRADICTION LIST

   Three direct conflicts exist between /project-docs/ and PDF requirements:

   CONTRADICTION A -- Employee Status Representation
     PDF Section:  3.4.1
     PDF Requires: Status field with values Active / On Leave / Retired
     Docs Model:   deleted_at (soft delete) + date_of_leaving (retirement proxy)
                   in 04_employee_schema.txt
     Conflict:     The soft-delete and date_of_leaving pattern cannot represent
                   the "On Leave" status. An employee on leave must remain active
                   in the system but be distinguishable from fully-active staff.
                   The current schema provides no mechanism for this state.

   CONTRADICTION B -- DC Declaration Review Actions
     PDF Section:  3.5.3 step (2)
     PDF Requires: DC can accept, query, OR flag for physical verification (3 named actions)
     Docs Model:   DC actions are APPROVED, CLARIFICATION_REQUESTED, REJECTED
                   in 05_workflows_and_states/00_state_machines.txt
     Conflict:     Docs substitute REJECTED for "flag for physical verification"
                   as the third DC action. The PDF does not mention REJECTED as
                   a DC action during the declaration review stage; it specifies
                   physical verification flagging.

   CONTRADICTION C -- Dashboard Status Labels
     PDF Section:  4.4
     PDF Requires: Display labels: Not Started / In Progress / Submitted /
                   Approved / Rejected
     Docs Model:   Internal states: DRAFT / PENDING_REVIEW / APPROVED /
                   REJECTED / SUPERSEDED in 05_workflows_and_states/00_state_machines.txt
     Conflict:     "In Progress" (PDF) and "Submitted" (PDF) have no direct state
                   equivalents in the documented state machine. DRAFT is used where
                   PDF expects Not Started, and PENDING_REVIEW is used where PDF
                   expects Submitted. The display-layer label mapping is absent.

5. IMPLEMENTATION READINESS ASSESSMENT

   Assessment: NOT READY -- functional gaps

   Rationale:
   The documentation covers the system's architectural skeleton and security
   posture completely. However, three categories of functional gaps require
   resolution before implementation can proceed with confidence:

   (a) SCHEMA COMPLETENESS -- ASSET DECLARATIONS (PDF 3.5.1, 3.5.2)
       The primary transparency and accountability feature of the system --
       asset declarations -- stores all structured field data in two unstructured
       TEXT columns (immovable_assets, movable_assets). The PDF defines 4
       immovable asset sub-types each with distinct required fields, and 5
       movable asset categories each with distinct required fields. None of
       these structured fields are present in the schema DDL. Implementation
       against this schema would produce a system that cannot enforce field-level
       validation or support structured audit queries on declared assets.

   (b) TEMPLE PROFILE FIELDS (PDF 3.2.1)
       8 of 10 field categories from PDF section 3.2.1 are absent from the
       temple core schema DDL. GPS coordinates, alias names, religious tradition,
       contact person, photograph, languages of worship, and linked mutts are
       all required display fields on the DC's primary temple profile view.
       They are also required input fields for Temple Authority. Implementation
       without these fields would produce an incomplete profile module.

   (c) WORKFLOW GAP -- PHYSICAL VERIFICATION (PDF 3.5.3)
       The state machine documented in 05_workflows_and_states/00_state_machines.txt
       defines three DC actions for declaration review: APPROVED, CLARIFICATION_
       REQUESTED, REJECTED. The PDF names "flag for physical verification" as the
       third action, not REJECTED. This is not a labelling issue; physical
       verification flagging and rejection serve different administrative
       functions. The state machine is incomplete and would produce a DC portal
       that does not conform to the PDF workflow specification.

   These three gaps would cause implementers to build incorrect schemas and
   incomplete state machines if development began today using only /project-docs/
   as the specification source.
