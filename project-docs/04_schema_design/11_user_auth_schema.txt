1. PURPOSE

   Define the users and refresh_tokens tables. Document password policy
   enforcement, MFA fields, and account lockout columns.

--------------------------------------------------------------------------------

3. DETAILED CONTENT

   3.1 users

   CREATE TABLE users (
     id                      BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
     username                VARCHAR(100)     NOT NULL,
     email                   VARCHAR(255)     NOT NULL,
     password_hash           VARCHAR(255)     NOT NULL,  -- bcrypt cost >= 12
     role                    ENUM('SUPER_ADMIN','DISTRICT_COLLECTOR',
                                  'DC_STAFF','TEMPLE_AUTHORITY') NOT NULL,
     -- Jurisdiction / ownership binding
     district_id             BIGINT UNSIGNED  DEFAULT NULL,  -- required for DC roles
     temple_id               BIGINT UNSIGNED  DEFAULT NULL,  -- required for TEMPLE_AUTHORITY
     -- Account state
     is_active               TINYINT(1)       NOT NULL DEFAULT 1,
     failed_login_count      TINYINT UNSIGNED NOT NULL DEFAULT 0,
     locked_until            DATETIME(6)      DEFAULT NULL,   -- NULL = not locked
     -- MFA
     mfa_enabled             TINYINT(1)       NOT NULL DEFAULT 0,
     mfa_type                ENUM('TOTP','SMS_OTP') DEFAULT NULL,
     mfa_secret_encrypted    TEXT             DEFAULT NULL,   -- AES-256 via KMS
     mfa_phone               VARCHAR(15)      DEFAULT NULL,   -- for SMS_OTP
     -- Activity
     last_login_at           DATETIME(6)      DEFAULT NULL,
     password_changed_at     DATETIME(6)      DEFAULT NULL,
     -- Token revocation (used for instant session invalidation on district transfer)
     token_revoked_before    DATETIME(6)      DEFAULT NULL,  -- JwtFilter rejects tokens issued before this timestamp
     -- Audit
     created_at              DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
     updated_at              DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                                          ON UPDATE CURRENT_TIMESTAMP(6),
     created_by              BIGINT UNSIGNED  NOT NULL,
     updated_by              BIGINT UNSIGNED  NOT NULL,
     PRIMARY KEY (id),
     UNIQUE KEY uq_username (username),
     UNIQUE KEY uq_email (email),
     CONSTRAINT fk_user_district FOREIGN KEY (district_id)
       REFERENCES geo_districts(id),
     CONSTRAINT fk_user_temple FOREIGN KEY (temple_id)
       REFERENCES temples(id),
     INDEX idx_user_role (role, is_active),
     INDEX idx_user_locked (locked_until)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

   TOKEN_REVOKED_BEFORE ENFORCEMENT (JwtAuthenticationFilter):
   When a DC is transferred to a new district by SUPER_ADMIN, the service sets:
     UPDATE users SET token_revoked_before = NOW(6), district_id = :newDistrictId
     WHERE id = :userId;
   All active refresh tokens are simultaneously revoked:
     UPDATE refresh_tokens SET revoked_at = NOW(6) WHERE user_id = :userId AND revoked_at IS NULL;
   JwtAuthenticationFilter check (added after signature verification):
     if (user.tokenRevokedBefore != null &&
         tokenIssuedAt.isBefore(user.tokenRevokedBefore.toInstant())) {
       throw new TokenRevokedException();  // --> 401
     }
   Effect: existing access tokens (up to 15 min old) are invalidated immediately.
   No grace period; revocation is instantaneous per security requirement SC-E1.
   Audit log entry: table=users, operation=UPDATE, action=DISTRICT_REASSIGNMENT.

   3.2 refresh_tokens

   CREATE TABLE refresh_tokens (
     id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
     user_id             BIGINT UNSIGNED NOT NULL,
     token_hash          VARCHAR(64)     NOT NULL,  -- SHA-256 hex of raw token
     issued_at           DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
     expires_at          DATETIME(6)     NOT NULL,
     revoked_at          DATETIME(6)     DEFAULT NULL,  -- NULL = active
     device_fingerprint  VARCHAR(500)    DEFAULT NULL,
     ip_address          VARCHAR(45)     DEFAULT NULL,
     created_at          DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
     updated_at          DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                                     ON UPDATE CURRENT_TIMESTAMP(6),
     created_by          BIGINT UNSIGNED NOT NULL,
     updated_by          BIGINT UNSIGNED NOT NULL,
     PRIMARY KEY (id),
     UNIQUE KEY uq_token_hash (token_hash),
     INDEX idx_rt_user_active (user_id, revoked_at, expires_at),
     CONSTRAINT fk_rt_user FOREIGN KEY (user_id) REFERENCES users(id)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

   3.4 mfa_recovery_codes  -- SUPER_ADMIN LOCKOUT PREVENTION

   Generated at MFA setup time. 8 single-use recovery codes per user.
   Used only when the primary MFA device is unavailable.

   CREATE TABLE mfa_recovery_codes (
     id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
     user_id             BIGINT UNSIGNED NOT NULL,
     code_hash           VARCHAR(72)     NOT NULL,  -- bcrypt of plain code; cost >= 12
     used_at             DATETIME(6)     DEFAULT NULL,  -- NULL = available; NOT NULL = consumed
     created_at          DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
     PRIMARY KEY (id),
     INDEX idx_rc_user (user_id, used_at),
     CONSTRAINT fk_rc_user FOREIGN KEY (user_id) REFERENCES users(id)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

   GENERATION:
   - On MFA setup (TOTP or SMS_OTP enabled), generate 8 cryptographically random
     10-character alphanumeric codes (e.g. 'X3K7-PM2Q-9A').
   - The raw codes are shown ONCE to the user (displayed in UI, never stored plaintext).
   - Each code is bcrypt-hashed and stored as mfa_recovery_codes rows.

   CONSUMPTION:
   POST /api/auth/mfa-verify { tempToken, mfaCode, isRecoveryCode: true }
   Service logic:
     1. Load all unused recovery codes for user (used_at IS NULL)
     2. For each: if (bcrypt.verify(submittedCode, row.code_hash)) -> mark used_at = NOW()
     3. On successful recovery code use: log to audit_auth_events (event_type='MFA_RECOVERY_USED')
     4. Force password + MFA re-enrollment flag on next login
     5. Insert SUPER_ADMIN in-app notification: "Recovery code used for account {username}"

   REGENERATION:
   POST /api/auth/recovery-codes/regenerate  (Authenticated; any role)
   - Requires current MFA verification before regenerating
   - Marks all existing recovery codes used_at = NOW() (invalidates old set)
   - Returns 8 new plain codes (shown once)

   SUPER_ADMIN RECOVERY PROCEDURE (when SUPER_ADMIN loses both TOTP and all recovery codes):
   - Requires in-person identity verification at HR&CE department
   - System administrator (infra team) runs bootstrap SQL to reset MFA for SA account:
       UPDATE users SET mfa_enabled = 0, mfa_secret_encrypted = NULL WHERE role = 'SUPER_ADMIN';
       DELETE FROM mfa_recovery_codes WHERE user_id = :sa_user_id;
   - This procedure is documented in the DR runbook (10_delivery_and_ops/).
   - Event is logged manually in audit_auth_events post-reset.

   3.5 ACCOUNT LOCKOUT LOGIC (APPLICATION LAYER)

   On LOGIN FAILURE:
     UPDATE users
     SET failed_login_count = failed_login_count + 1,
         locked_until = CASE
           WHEN failed_login_count + 1 >= 5
           THEN DATE_ADD(NOW(6), INTERVAL 30 MINUTE)
           ELSE locked_until
         END
     WHERE id = :user_id;

   On LOGIN SUCCESS:
     UPDATE users
     SET failed_login_count = 0,
         locked_until = NULL,
         last_login_at = NOW(6)
     WHERE id = :user_id;

   Lock check (before authentication):
     SELECT locked_until FROM users WHERE username = :username;
     IF locked_until IS NOT NULL AND locked_until > NOW(6)
       THEN return HTTP 423 (Locked) with retry_after timestamp

   3.4 JWT TOKEN STRUCTURE

   Access Token:
     - Expiry: 15 minutes
     - Claims: sub (user_id), role, district_id, temple_id, jti
     - Algorithm: RS256 (asymmetric; private key on backend only)

   Refresh Token:
     - Expiry: 7 days
     - Opaque random UUID (512 bits)
     - Stored as SHA-256 hash in refresh_tokens table
     - Rotate on every use (old token revoked, new token issued)

   3.5 SESSION TIMEOUT

   - Backend: Access token TTL = 15 minutes (hard expiry)
   - Frontend: React Query detects 401 response, attempts silent refresh
               using cached refresh token
   - If refresh fails (token expired/revoked): redirect to login
   - Activity timeout: if user is idle for 25 minutes, show warning modal
     "Your session expires in 5 minutes" with "Stay logged in" button that
     calls the /auth/refresh endpoint

--------------------------------------------------------------------------------

4. DECISIONS LOCKED

   - bcrypt cost factor >= 12 for password_hash AND recovery code hashes
   - Refresh tokens stored as SHA-256 hash only (raw token never in DB)
   - Access token: RS256 asymmetric JWT, 15-minute TTL
   - Refresh token: 7-day TTL, opaque, single-use rotation; stored in HttpOnly cookie (see 06_security_and_auth/00_auth_architecture.txt)
   - Account lockout: 5 failed attempts -> 30-minute lockout
   - token_revoked_before: set immediately on district transfer; no grace period; all refresh tokens simultaneously revoked
   - mfa_recovery_codes: 8 codes generated at MFA setup; bcrypt-hashed; single-use; regeneration requires active MFA

6. RISKS & EDGE CASES

   - Refresh token theft: if a stolen token is used before the legitimate user,
     the rotation invalidates both. The legitimate user is logged out, alerting
     them to the breach. Log both usages in audit_auth_events.
   - TOTP clock skew: allow +/- 1 time step (30 seconds) tolerance in
     TOTP verification.
   - Orphaned registration: If Aadhaar OTP expires mid-registration, a user
     record (status=PENDING_ACTIVATION) + temple record (status=DRAFT) are left
     orphaned. A nightly cleanup job (JOB-08, TODO) should purge
     PENDING_ACTIVATION users older than 24 hours and their linked DRAFT temples
     where no further action has occurred.
   - SUPER_ADMIN MFA device loss: recovery procedure relies on mfa_recovery_codes
     (see 3.4). If all 8 codes are consumed, SUPER_ADMIN must follow the
     in-person recovery procedure documented in 10_delivery_and_ops/ DR runbook.

--------------------------------------------------------------------------------

7. ASSUMPTIONS

   - users.created_by: for the first SUPER_ADMIN created during bootstrap,
     set created_by = own id (self-referential; handle in DB seed script)
   - Aadhaar eKYC verification is a separate flow from standard login MFA;
     it is performed only during initial user registration
