1. PURPOSE

   Define the notification_events queue table and in_app_notifications table.
   The notification system uses a DB-based queue (not SQS) for v1.

--------------------------------------------------------------------------------

3. DETAILED CONTENT

   3.1 notification_events - OUTBOUND QUEUE

   CREATE TABLE notification_events (
     id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
     recipient_user_id   BIGINT UNSIGNED NOT NULL,
     template_key        VARCHAR(100)    NOT NULL,
     template_params     JSON            DEFAULT NULL,
     channels            JSON            NOT NULL,   -- e.g. ["EMAIL","SMS","IN_APP"]
     priority            TINYINT UNSIGNED NOT NULL DEFAULT 5,  -- 1 (high) to 10 (low)
     status              ENUM('PENDING','PROCESSING','SENT','FAILED','SKIPPED')
                         NOT NULL DEFAULT 'PENDING',
     -- Per-channel tracking
     email_status        ENUM('PENDING','SENT','FAILED','SKIPPED') DEFAULT 'PENDING',
     sms_status          ENUM('PENDING','SENT','FAILED','SKIPPED') DEFAULT 'PENDING',
     in_app_status       ENUM('PENDING','SENT','FAILED','SKIPPED') DEFAULT 'PENDING',
     -- Retry
     attempt_count       TINYINT UNSIGNED NOT NULL DEFAULT 0,
     max_attempts        TINYINT UNSIGNED NOT NULL DEFAULT 3,
     next_retry_at       DATETIME(6)      DEFAULT NULL,
     last_error          TEXT             DEFAULT NULL,
     -- Timestamps
     created_at          DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
     updated_at          DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                                     ON UPDATE CURRENT_TIMESTAMP(6),
     created_by          BIGINT UNSIGNED NOT NULL,
     updated_by          BIGINT UNSIGNED NOT NULL,
     PRIMARY KEY (id),
     INDEX idx_notif_pending (status, priority, next_retry_at),
     INDEX idx_notif_user (recipient_user_id, created_at),
     CONSTRAINT fk_notif_user FOREIGN KEY (recipient_user_id) REFERENCES users(id)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

   3.2 in_app_notifications - READ/UNREAD INBOX

   CREATE TABLE in_app_notifications (
     id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
     recipient_user_id   BIGINT UNSIGNED NOT NULL,
     notification_event_id BIGINT UNSIGNED DEFAULT NULL,
     title               VARCHAR(255)    NOT NULL,
     body                TEXT            NOT NULL,
     link_url            VARCHAR(500)    DEFAULT NULL,
     is_read             TINYINT(1)      NOT NULL DEFAULT 0,
     read_at             DATETIME(6)     DEFAULT NULL,
     created_at          DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
     updated_at          DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                                     ON UPDATE CURRENT_TIMESTAMP(6),
     created_by          BIGINT UNSIGNED NOT NULL,
     updated_by          BIGINT UNSIGNED NOT NULL,
     PRIMARY KEY (id),
     INDEX idx_inapp_user_unread (recipient_user_id, is_read, created_at),
     CONSTRAINT fk_inapp_user FOREIGN KEY (recipient_user_id) REFERENCES users(id)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

   3.6 SERVICE-LAYER TRIGGER MAP

   Exactly which service method inserts which notification_event row.
   All INSERTs use NotificationService.createEvent(templateKey, recipientUserId, params).
   NotificationService handles recipient resolution, channel determination, and DB write.

   Trigger Site                                     | Template Key                        | Recipient Resolution
   -------------------------------------------------|-------------------------------------|---------------------------------------------------
   DeclarationService.submit()                      | DECLARATION_SUBMITTED               | DC_in_district = users WHERE role='DC' AND district_id = temple.district_id
   DeclarationService.approve()                     | DECLARATION_APPROVED                | temple.contact_user_id (TA who owns temple)
   DeclarationService.approve()                     | DECLARATION_ACKNOWLEDGEMENT_READY   | temple.contact_user_id (same TA, second event)
   DeclarationService.reject()                      | DECLARATION_REJECTED                | temple.contact_user_id
   DeclarationService.requestClarification()        | DECLARATION_CLARIFICATION_REQ       | temple.contact_user_id
   DeclarationService.resubmit()                    | DECLARATION_CLARIFICATION_REPLY     | DC_in_district (same lookup as submit)
   DeclarationService.flagPhysicalVerification()    | DECLARATION_PHYSICAL_VERIFICATION   | temple.contact_user_id
   OverdueDeclarationJob.run()                      | DECLARATION_OVERDUE                 | temple.contact_user_id (one per overdue temple found)
   PreDeadlineReminderJob.run() [7-day window]      | DECLARATION_OVERDUE_REMINDER_7D     | temple.contact_user_id
   PreDeadlineReminderJob.run() [30-day window]     | DECLARATION_OVERDUE_REMINDER_30D    | temple.contact_user_id
   TempleProfileService.approveProfile()            | PROFILE_APPROVED                    | temple.contact_user_id
   TempleProfileService.rejectProfile()             | PROFILE_REJECTED                    | temple.contact_user_id
   UserService.createUser()                         | USER_REGISTERED                     | newly created user.id
   AuthService.initiatePasswordReset()              | PASSWORD_RESET                      | user matching the submitted email
   AuthService.lockAccount()                        | ACCOUNT_LOCKED                      | user whose account was locked
   NotificationDispatcher [after max retries]       | NOTIFICATION_DELIVERY_FAILED        | all users WHERE role = 'SUPER_ADMIN'

   DC RECIPIENT RESOLUTION — detailed logic (for DECLARATION_SUBMITTED and CLARIFICATION_REPLY):
     SELECT u.id FROM users u
     WHERE u.role = 'DISTRICT_COLLECTOR'
     AND u.district_id = (SELECT t.district_id FROM temples t WHERE t.id = :templeId)
     AND u.is_active = 1
     AND u.is_deleted = 0
   If the query returns multiple DCs (should not happen but guard exists),
   create one notification_event per DC.
   If no DC found (district unassigned), log WARN and INSERT a NOTIFICATION_DELIVERY_FAILED
   event targeting SUPER_ADMIN immediately (do not wait for retry).

   NotificationService.createEvent() signature (Java):
     void createEvent(
       String templateKey,
       Long recipientUserId,
       Map<String, String> templateParams
     );
   Implementation note: channel list is looked up from the template registry (hardcoded
   enum or DB table). All DB writes to notification_events MUST be done in the same
   @Transactional scope as the parent service method (e.g., approve(), submit()).
   This ensures the notification is always created if the business operation succeeds,
   and rolled back if the operation fails.

   3.4 RETRY STRATEGY

   Attempt 1: Immediate on creation (attempt_count = 0)
   Attempt 2: next_retry_at = created_at + 2 minutes
   Attempt 3: next_retry_at = last_attempt + 10 minutes
   After 3 failures: status = FAILED; INSERT a NOTIFICATION_DELIVERY_FAILED
     event targeting SUPER_ADMIN (IN_APP only, no recursive retry).

   DELIVERY FAILURE HANDLING:
   - Per-channel failure is tracked independently (email_status, sms_status, in_app_status)
   - If email_status = FAILED but sms_status = SENT, overall status = SENT (partial delivery ok)
   - status = FAILED only when ALL requested channels are in FAILED or SKIPPED state
     AND attempt_count >= max_attempts
   - SUPER_ADMIN IN_APP notification is raised once per failed event (not per retry)

   Priority Matrix:
     Priority 1-3 (CRITICAL):  ACCOUNT_LOCKED, PASSWORD_RESET
     Priority 4-6 (HIGH):      DECLARATION_SUBMITTED, APPROVED, REJECTED,
                                CLARIFICATION_REQUESTED, OVERDUE
     Priority 7-10 (NORMAL):   REMINDERS, PROFILE events, USER_REGISTERED

   3.5 SCHEDULER QUERY (POLLING)

   Scheduled every 30 seconds (Spring @Scheduled):
   SELECT * FROM notification_events
   WHERE status = 'PENDING'
   AND (next_retry_at IS NULL OR next_retry_at <= NOW(6))
   ORDER BY priority ASC, created_at ASC
   LIMIT 50;

4. DECISIONS LOCKED

   - DB-based queue (notification_events table) for v1; no SQS dependency
   - Max 3 retry attempts with exponential backoff (immediate, +2min, +10min)
   - In-app notifications stored in in_app_notifications table
   - Email: EmailGateway interface — NoOpEmailGateway/MailHog (dev) / SesEmailGateway (prod)
   - SMS: SmsGateway interface — ConsoleSmsGateway (dev) / SnsGateway (prod)
   - All notification INSERTs occur in the same @Transactional scope as the triggering service method
   - NotificationService.createEvent() is the single entry point; callers never insert directly

--------------------------------------------------------------------------------

5. OPEN QUESTIONS

   - RESOLVED: notification_events is not partitioned in v1; partition by created_at
     can be added via Flyway migration if table grows beyond 1M rows.
   - RESOLVED: SUPER_ADMIN is alerted via IN_APP notification (see NOTIFICATION_DELIVERY_FAILED
     template). Failures also logged at WARN level by NotificationDispatcher.
   - RESOLVED: SMS notifications are in English (short summaries). Kannada translations
     can be added in v2 if HRCE department requests it.

--------------------------------------------------------------------------------

6. RISKS & EDGE CASES

   - If AWS SES is in sandbox mode, emails only go to verified addresses.
     Request SES production access early (1-2 week AWS process).
   - Phone number format for SNS: must be E.164 (+91XXXXXXXXXX). Validate
     at the users table level.

--------------------------------------------------------------------------------

7. ASSUMPTIONS

   - Email content is in English; SMS is a shorter English summary
   - Template rendering uses a simple key-value param substitution (String.replace("{key}", value))
   - Notification delivery is best-effort; no guaranteed delivery SLA for v1
   - For dev environment: all email goes through MailHog (visible at localhost:8025);
     all SMS is printed to application log (ConsoleSmsGateway)
