1. PURPOSE

   Document the complete state transition model for all 5 workflow modules:
   Temple Profile, Asset Declarations, Trust, Employees, and Contractors.
   For each module: states, transitions, guard conditions, and role permissions.

--------------------------------------------------------------------------------

3. DETAILED CONTENT

   3.1 TEMPLE PROFILE STATE MACHINE

   States: DRAFT, PENDING_REVIEW, APPROVED, REJECTED, SUPERSEDED

   Transitions:
   FROM              | TO               | ACTOR          | GUARD
   ------------------|------------------|----------------|-----------------------------
   (new)             | DRAFT            | TEMPLE_AUTH    | Temple must be registered
   DRAFT             | PENDING_REVIEW   | TEMPLE_AUTH    | Required fields complete
   PENDING_REVIEW    | APPROVED         | DC / SA        | DC in same district
   PENDING_REVIEW    | REJECTED         | DC / SA        | DC in same district
   PENDING_REVIEW    | CLARIFICATION*   | -              | (see 01_clarification_loop.txt)
   REJECTED          | DRAFT            | TEMPLE_AUTH    | Max versions not exceeded
   APPROVED          | SUPERSEDED       | SYSTEM         | On new version approval
   Any               | SUPERSEDED       | SYSTEM         | On newer version approved

   * Profile does not use CLARIFICATION_REQUESTED status; only Asset Declarations do.
     DC rejects with a comment; Temple creates new version.

   Action visibility matrix:
   State             | TEMPLE_AUTH          | DC / DC_STAFF       | SUPER_ADMIN
   ------------------|----------------------|---------------------|------------------
   DRAFT             | View, Edit, Delete   | -                   | View
   PENDING_REVIEW    | View (read-only)     | View, Approve/Reject| View, Override
   APPROVED          | View                 | View                | View, Edit
   REJECTED          | View, Create new     | View                | View, Override
   SUPERSEDED        | View (history)       | View (history)      | View

   3.2 ASSET DECLARATION STATE MACHINE

   States: DRAFT, PENDING_REVIEW, APPROVED, CLARIFICATION_REQUESTED,
           PHYSICAL_VERIFICATION_REQUESTED, REJECTED, SUPERSEDED

   Transitions:
   FROM                             | TO                              | ACTOR       | GUARD
   ---------------------------------|---------------------------------|-------------|---------------------
   (new)                            | DRAFT                           | TEMPLE_AUTH | Temple active,
                                    |                                 |             | no APPROVED for year
   DRAFT                            | PENDING_REVIEW                  | TEMPLE_AUTH | Required fields OK;
                                    |                                 |             | snapshot_json written
   PENDING_REVIEW                   | APPROVED                        | DC          | DC in district
   PENDING_REVIEW                   | CLARIFICATION_REQUESTED         | DC          | DC in district
   PENDING_REVIEW                   | PHYSICAL_VERIFICATION_REQUESTED | DC          | DC in district
   PENDING_REVIEW                   | REJECTED                        | DC          | DC in district
   CLARIFICATION_REQUESTED          | PENDING_REVIEW                  | TEMPLE_AUTH | Clarification reply
                                    |                                 |             | submitted
   PHYSICAL_VERIFICATION_REQUESTED  | APPROVED                        | DC, SA      | Physical visit done;
                                    |                                 |             | DC records findings
   PHYSICAL_VERIFICATION_REQUESTED  | REJECTED                        | DC, SA      | DC refuses after
                                    |                                 |             | physical inspection
   REJECTED                         | DRAFT (new version)             | TEMPLE_AUTH | version_number+1
   APPROVED                         | (terminal)                      | -           | No transitions out
   Any active                       | SUPERSEDED                      | SYSTEM      | Newer version approved

   DC ACTIONS MAPPED TO PDF TERMINOLOGY:
     PDF "accept"                     -> transition to APPROVED
     PDF "query"                      -> transition to CLARIFICATION_REQUESTED
     PDF "flag for physical verify"   -> transition to PHYSICAL_VERIFICATION_REQUESTED

   PHYSICAL_VERIFICATION_REQUESTED RULES:
     - DC must record findings in declaration_clarifications
       (direction='DC_TO_TEMPLE', section_name='PHYSICAL_VERIFICATION')
     - No time limit defined for v1; SUPER_ADMIN flagged if > 30 days in this state
     - Only DC from the same district (or SA) may set and clear this state

   3.3 TRUST MODULE STATE MACHINE

   Trust Registration States: ACTIVE, DISSOLVED

   Transitions:
   ACTIVE -> DISSOLVED: TEMPLE_AUTH or SUPER_ADMIN (no DC approval needed)

   Trust Approval Workflow:
   Trust data is DIRECT-SAVE (no staging/approval cycle in v1). Changes made
   by TEMPLE_AUTH are immediately visible to DC. This is consistent with
   03_trust_schema.txt which has no staging tables. DC reviews trust data
   in read-only mode only.

   Board Member States: active (is_active=1), historical (is_active=0)

   Transitions:
   active -> historical: Set cessation_date; is_active = 0
                         Actor: TEMPLE_AUTH

   Trust Financials: Submitted once per year; no status field.
                     Immutable after submission.

   3.4 EMPLOYEE STATE MACHINE

   Employment Status (employment_status column): ACTIVE, ON_LEAVE, RETIRED, RESIGNED
   Logical Delete (deleted_at): used only for account-level deactivation by SUPER_ADMIN

   Transitions:
   FROM          | TO         | ACTOR          | NOTES
   --------------|------------|----------------|-----------------------------------------------
   (new record)  | ACTIVE     | TEMPLE_AUTH    | Auto on creation
   ACTIVE        | ON_LEAVE   | TEMPLE_AUTH    | Temporary absence; no date_of_leaving set
   ON_LEAVE      | ACTIVE     | TEMPLE_AUTH    | Return from leave
   ACTIVE        | RETIRED    | TEMPLE_AUTH    | Set date_of_leaving; record remains visible
   ACTIVE        | RESIGNED   | TEMPLE_AUTH    | Set date_of_leaving; record remains visible
   Any status    | deleted    | SUPER_ADMIN    | Set deleted_at (account-level; not business state)

   GUARD CONDITIONS:
   - TEMPLE_AUTH can only transition employees of their own temple
   - A RETIRED or RESIGNED employee cannot transition back to ACTIVE
     (create a new employee record for re-employment)
   - deleted_at must never be set by TEMPLE_AUTH (SA only)

   3.5 CONTRACTOR STATE MACHINE

   States: active (deleted_at IS NULL), ended (deleted_at IS NOT NULL)

   Transitions:
   active -> ended: Set deleted_at, deleted_by; optionally set contract_end_date
                    Actor: TEMPLE_AUTH

--------------------------------------------------------------------------------

4. DECISIONS LOCKED

   - Asset declarations: APPROVED is a terminal state; no modifications after
   - SUPERSEDED: set by SYSTEM only (not directly by any user role)
   - Employee/contractor records: no approval workflow; direct TEMPLE_AUTH management
   - Trust first registration: auto-ACTIVE on creation (no DC approval in v1)

--------------------------------------------------------------------------------

5. OPEN QUESTIONS

   - Should DC be able to reopen an APPROVED declaration (e.g., if fraud
     discovered post-approval)?
   - Is there a maximum number of REJECTED versions before a temple is
     automatically flagged for SUPER_ADMIN review?

--------------------------------------------------------------------------------

6. RISKS & EDGE CASES

   - Race condition: Two DCs from same district (or DC + SUPER_ADMIN) review
     the same declaration simultaneously. Use optimistic locking (version
     column) on asset_declarations to detect conflicts.
   - CLARIFICATION_REQUESTED loop: No limit defined on number of rounds.
     Add a counter (clarification_round column) and alert SA if > 3 rounds.

--------------------------------------------------------------------------------

7. ASSUMPTIONS

   - A temple can have at most one PENDING_REVIEW declaration per financial year
   - All state transitions are validated at the service layer (not only DB)
   - State transition history is captured via audit_data_events
