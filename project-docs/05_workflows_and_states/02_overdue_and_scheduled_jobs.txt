1. PURPOSE

   Document all scheduled background jobs in the TRM system, their trigger
   schedules, and the overdue declaration detection logic.

--------------------------------------------------------------------------------

3. DETAILED CONTENT

   3.1 SCHEDULED JOBS REGISTRY

   Job ID | Name                      | Cron Schedule    | Description
   -------|---------------------------|------------------|---------------------------
   JOB-01 | OverdueDeclarationScanner | 0 5 0 1 4 *      | Mark overdue on Apr 1;
          |                           |                  | runs once per year
   JOB-02 | OverdueReminderJob        | 0 0 8 * * *      | Daily 8am; send email/SMS
          |                           |                  | reminders for overdue
   JOB-03 | PreDeadlineReminderJob    | 0 0 8 * * *      | Daily 8am; send 30-day,
          |                           |                  | 7-day, 1-day warnings
   JOB-04 | NotificationProcessorJob  | */30 * * * * *   | Every 30 sec; process
          |                           |                  | pending notification_events
   JOB-05 | TokenCleanupJob           | 0 0 2 * * *      | Daily 2am; purge expired
          |                           |                  | refresh_tokens
   JOB-06 | SearchSummaryRebuildJob   | 0 0 3 * * *      | Daily 3am; full rebuild
          |                           |                  | of temple_search_summary

   3.2 JOB-01: OVERDUE DECLARATION SCANNER

   Trigger: April 1 at 00:05 (start of new financial year)
   Cron: 0 5 0 1 4 *

   Logic:
     -- Financial year ended March 31. On April 1, scan for non-approved
     -- declarations for the year just ended.
     DECLARE prev_year = CONCAT(YEAR(NOW()) - 1, '-', RIGHT(YEAR(NOW()), 2));

     UPDATE asset_declarations
     SET is_overdue = 1,
         overdue_flagged_at = NOW(6)
     WHERE financial_year = prev_year
     AND status NOT IN ('APPROVED')
     AND is_overdue = 0;

     -- For each flagged temple, insert a notification event
     INSERT INTO notification_events (recipient_user_id, template_key,
       template_params, channels, priority, status, created_by, updated_by)
     SELECT u.id, 'DECLARATION_OVERDUE',
            JSON_OBJECT('year', prev_year, 'temple_id', d.temple_id),
            '["EMAIL","SMS","IN_APP"]', 2, 'PENDING', 1, 1
     FROM asset_declarations d
     JOIN users u ON u.temple_id = d.temple_id
     WHERE d.financial_year = prev_year
     AND d.is_overdue = 1
     AND u.role = 'TEMPLE_AUTHORITY';

     -- Refresh search summary for affected temples
     -- (via async service call, not inline SQL)

   3.3 JOB-03: PRE-DEADLINE REMINDER

   Trigger: Daily at 8am
   Logic:
     - Financial year end = March 31
     - Check if today is 30, 7, or 1 day(s) before March 31
     - Find temples with no APPROVED or PENDING_REVIEW declaration
       for the current financial year
     - Insert DECLARATION_OVERDUE_REMINDER_30D / _7D notification events

   3.4 JOB-04: NOTIFICATION PROCESSOR

   Trigger: Every 30 seconds
   Logic:
     SELECT * FROM notification_events
     WHERE status = 'PENDING'
     AND (next_retry_at IS NULL OR next_retry_at <= NOW(6))
     ORDER BY priority ASC, created_at ASC
     LIMIT 50
     FOR UPDATE SKIP LOCKED;  -- prevents double-processing

   For each row:
     1. UPDATE status = 'PROCESSING'
     2. For each channel in channels JSON:
        - EMAIL: call AWS SES SendEmail API
        - SMS: call AWS SNS Publish API
        - IN_APP: INSERT into in_app_notifications
     3. On success: UPDATE individual channel status = 'SENT'
     4. On all channels sent: UPDATE status = 'SENT'
     5. On failure: UPDATE attempt_count + 1;
        IF attempt_count >= max_attempts: status = 'FAILED'
        ELSE: next_retry_at = retry schedule

   3.5 JOB-05: TOKEN CLEANUP

   Trigger: Daily at 2am
   Logic:
     DELETE FROM refresh_tokens
     WHERE (expires_at < NOW(6) OR revoked_at IS NOT NULL)
     AND created_at < DATE_SUB(NOW(6), INTERVAL 7 DAY);
     -- Keep recent revoked tokens for 7 days for audit purposes

   3.6 JOB-06: SEARCH SUMMARY REBUILD

   Trigger: Daily at 3am
   Logic: Full rebuild of temple_search_summary (see schema file 10).
   Note: This is a safety net; event-driven refresh keeps it current
         throughout the day.

--------------------------------------------------------------------------------

4. DECISIONS LOCKED

   - All jobs implemented as Spring @Scheduled methods
   - JOB-04 uses FOR UPDATE SKIP LOCKED to handle concurrent executions safely
   - JOB-01 cron targets April 1 (Indian financial year start)
   - Notification processing batched at 50 records per execution cycle

--------------------------------------------------------------------------------

5. OPEN QUESTIONS

   - Should jobs run on all instances in a multi-instance deployment, or only
     on one instance? Use Spring's @SchedulerLock (ShedLock library) to prevent
     duplicate execution in clustered deployments.
   - Is there a requirement for job execution logs in the database?

--------------------------------------------------------------------------------

6. RISKS & EDGE CASES

   - If JOB-01 (overdue scanner) fails silently on April 1, temples are not
     flagged as overdue until the next run. Add a health check alert if
     JOB-01 does not record a successful run by April 1 06:00.
   - JOB-04 running every 30 seconds: if notification volume exceeds 50/min,
     queue backlog builds. Monitor queue depth and increase LIMIT or concurrency.

--------------------------------------------------------------------------------

7. ASSUMPTIONS

   - Server time is in IST (UTC+5:30) or cron schedules are adjusted for UTC
   - ShedLock is used to prevent duplicate job execution in multi-instance deploy
   - Spring @Scheduled(cron) supports 6-component expressions (sec min hr day month dow)
