   3.2 JOB-01: OVERDUE DECLARATION SCANNER

   Trigger: April 1 at 00:05 (start of new financial year)
   Cron: 0 5 0 1 4 *

   CRITICAL RULE: Only temples with status = DRAFT (i.e., never submitted)
   are overdue. Temples with status in (PENDING_REVIEW, CLARIFICATION_REQUESTED,
   PHYSICAL_VERIFICATION_REQUESTED) have submitted; the delay is DC-side.
   Marking those temples overdue is factually incorrect and must NOT occur.

   Logic:
     DECLARE prev_year = CONCAT(YEAR(NOW()) - 1, '-', RIGHT(YEAR(NOW()), 2));

     -- Case 1: Temple has a DRAFT declaration (submitted but not progressed)
     UPDATE asset_declarations
     SET is_overdue = 1,
         overdue_flagged_at = NOW(6)
     WHERE financial_year = prev_year
     AND status = 'DRAFT'             -- ONLY DRAFT; not PENDING_REVIEW etc.
     AND is_overdue = 0;

     -- Case 2: Temple has NO declaration at all for the year
     -- (handled by inserting a synthetic DRAFT record to represent the gap;
     --  see 04_schema_design/06_asset_declaration_schema.txt section 3.4)

     -- For each newly flagged temple, insert a notification event
     INSERT INTO notification_events (recipient_user_id, template_key,
       template_params, channels, priority, status, created_by, updated_by)
     SELECT u.id, 'DECLARATION_OVERDUE',
            JSON_OBJECT('year', prev_year, 'temple_id', d.temple_id),
            '["EMAIL","SMS","IN_APP"]', 2, 'PENDING', 1, 1
     FROM asset_declarations d
     JOIN users u ON u.temple_id = d.temple_id
     WHERE d.financial_year = prev_year
     AND d.is_overdue = 1
     AND u.role = 'TEMPLE_AUTHORITY'
     AND u.is_active = 1;            -- Skip deactivated users

   3.3 JOB-03: PRE-DEADLINE REMINDER

   Trigger: Daily at 8am
   Logic:
     - Financial year end = March 31
     - Check if today is 30, 7, or 1 day(s) before March 31
     - Find temples with no APPROVED or PENDING_REVIEW declaration
       for the current financial year
     - Insert DECLARATION_OVERDUE_REMINDER_30D / _7D notification events

   3.4 JOB-04: NOTIFICATION PROCESSOR

   Trigger: Every 30 seconds
   Logic:
     SELECT * FROM notification_events
     WHERE status = 'PENDING'
     AND (next_retry_at IS NULL OR next_retry_at <= NOW(6))
     ORDER BY priority ASC, created_at ASC
     LIMIT 50
     FOR UPDATE SKIP LOCKED;  -- prevents double-processing

   For each row:
     1. UPDATE status = 'PROCESSING'
     2. For each channel in channels JSON:
        - EMAIL: call EmailGateway.send(recipientEmail, templateKey, params)
            LOCAL DEV: logs email body to console (NoOpEmailGateway)
            PRODUCTION: delegates to AWS SES SendEmail API
        - SMS: call SmsGateway.send(phoneNumber, messageBody)
            LOCAL DEV: logs SMS body to console (ConsoleSmsGateway)
            PRODUCTION: delegates to AWS SNS Publish API
        - IN_APP: INSERT into in_app_notifications
     3. On success: UPDATE individual channel status = 'SENT'
     4. On all channels sent: UPDATE status = 'SENT'
     5. On failure: UPDATE attempt_count + 1;
        IF attempt_count >= max_attempts: status = 'FAILED'
        ELSE: next_retry_at = retry schedule

   3.5 JOB-05: TOKEN CLEANUP

   Trigger: Daily at 2am
   Logic:
     DELETE FROM refresh_tokens
     WHERE (expires_at < NOW(6) OR revoked_at IS NOT NULL)
     AND created_at < DATE_SUB(NOW(6), INTERVAL 7 DAY);
     -- Keep recent revoked tokens for 7 days for audit purposes

   3.6 JOB-06: SEARCH SUMMARY REBUILD (ATOMIC SHADOW TABLE SWAP)

   Trigger: Daily at 3am
   CRITICAL: Use shadow table + RENAME TABLE to prevent dirty reads during rebuild.
   A TRUNCATE + INSERT pattern leaves the table empty for seconds during rebuild,
   causing DC dashboard queries to return zero results. Use the following pattern:

   Logic:
     Step 1: Create shadow table (if not exists):
       CREATE TABLE IF NOT EXISTS temple_search_summary_rebuild LIKE temple_search_summary;

     Step 2: Truncate shadow table:
       TRUNCATE TABLE temple_search_summary_rebuild;

     Step 3: Populate shadow table (full JOIN query for all temples):
       INSERT INTO temple_search_summary_rebuild
         SELECT ... (same query as current rebuild logic)

     Step 4: Atomic swap:
       RENAME TABLE
         temple_search_summary TO temple_search_summary_old,
         temple_search_summary_rebuild TO temple_search_summary;

     Step 5: Drop old table:
       DROP TABLE temple_search_summary_old;

   CONCURRENT EVENT-DRIVEN UPDATES:
   Event-driven updates (on declaration submit/approve/reject) should target the
   LIVE table (temple_search_summary) using UPSERT (INSERT ... ON DUPLICATE KEY UPDATE).
   The atomic swap in step 4 replaces the live table; event-driven updates that arrive
   between steps 3 and 4 will target the pre-swap table and be lost in the swap.
   MITIGATION: After the RENAME, re-apply any pending event-driven updates by checking
   notification_events for events that occurred after the rebuild start time.
   Alternative: Use application-level distributed lock (Redis or DB advisory lock)
   around the 3am rebuild window to block event-driven updates for < 30 seconds.

   Note: This is a daily safety-net rebuild. Event-driven refresh keeps the summary
   current throughout the day via UPSERT calls in the service layer.

   3.7 JOB-07: PHYSICAL VERIFICATION SLA MONITOR

   Trigger: Daily at 9am
   Cron: 0 0 9 * * *

   Logic:
     -- Find declarations stuck in PHYSICAL_VERIFICATION_REQUESTED for > 30 days
     SELECT d.id, d.temple_id, d.financial_year, d.updated_at,
            t.name AS temple_name, dist.name AS district_name
     FROM asset_declarations d
     JOIN temples t ON t.id = d.temple_id
     JOIN geo_hoblis h ON h.id = t.hobli_id
     JOIN geo_taluks tal ON tal.id = h.taluk_id
     JOIN geo_districts dist ON dist.id = tal.district_id
     WHERE d.status = 'PHYSICAL_VERIFICATION_REQUESTED'
     AND d.updated_at < DATE_SUB(NOW(), INTERVAL 30 DAY);

     -- For each: insert SUPER_ADMIN in-app notification
     INSERT INTO notification_events (recipient_user_id, template_key,
       template_params, channels, priority, status, created_by, updated_by)
     SELECT sa.id, 'PHYSICAL_VERIFICATION_SLA_BREACH',
            JSON_OBJECT(
              'declaration_id', d.id,
              'temple_name', t.name,
              'district_name', dist.name,
              'days_pending', DATEDIFF(NOW(), d.updated_at)
            ),
            '["IN_APP","EMAIL"]', 1, 'PENDING', 1, 1
     FROM ... (same JOIN as above)
     JOIN users sa ON sa.role = 'SUPER_ADMIN' AND sa.is_active = 1;

   Idempotency: Check that no SLA notification was already sent in the last
   7 days for the same declaration_id before inserting (prevent duplicate alerts).

--------------------------------------------------------------------------------

4. DECISIONS LOCKED

   - All jobs implemented as Spring @Scheduled methods
   - JOB-04 uses FOR UPDATE SKIP LOCKED to handle concurrent executions safely
   - JOB-01 cron targets April 1 (Indian financial year start)
   - Notification processing batched at 50 records per execution cycle

--------------------------------------------------------------------------------

5. OPEN QUESTIONS

   - Should jobs run on all instances in a multi-instance deployment, or only
     on one instance? Use Spring's @SchedulerLock (ShedLock library) to prevent
     duplicate execution in clustered deployments.
   - Is there a requirement for job execution logs in the database?

--------------------------------------------------------------------------------

6. RISKS & EDGE CASES

   - If JOB-01 (overdue scanner) fails silently on April 1, temples are not
     flagged as overdue until the next run. Add a health check alert if
     JOB-01 does not record a successful run by April 1 06:00.
   - JOB-04 running every 30 seconds: if notification volume exceeds 50/min,
     queue backlog builds. Monitor queue depth and increase LIMIT or concurrency.

--------------------------------------------------------------------------------

7. ASSUMPTIONS

   - Server time is in IST (UTC+5:30) or cron schedules are adjusted for UTC
   - ShedLock is used to prevent duplicate job execution in multi-instance deploy
   - Spring @Scheduled(cron) supports 6-component expressions (sec min hr day month dow)
