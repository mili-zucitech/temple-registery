SECTION 1: MODULE OVERVIEW
1.1 PURPOSE

The District Collector (DC) Module provides a read-and-review portal for government-appointed District Collectors and their staff to inspect, search, and act on temple data within their assigned district. The module enforces strict geographic (district-level) data boundaries and drives the approval workflow for temple asset declarations and temple profile staging submissions.

1.2 RESPONSIBILITIES

Temple search across the assigned district with multi-attribute filters
Aggregated temple profile viewing (read-only) combining temple, trust, employees, contractors, asset declarations, and documents
Approval workflow execution on asset declarations: approve, reject, request clarification, flag for physical verification
Temple profile staging review: approve or reject profile submissions from Temple Authority
DC dashboard: KPI metrics, grade distribution, overdue alerts, recent activity feed
Notification inbox: view, mark as read, mark all as read
Export: generate PDF or CSV filtered temple reports, sync or async depending on volume
Current user context endpoint: provide role, district, and identity to the frontend
Geo hierarchy read endpoints: required by frontend filter dropdowns
1.3 BOUNDARIES - WHAT THIS MODULE DOES NOT INCLUDE

Authentication, MFA, token issuance, JWT filter, Spring Security configuration (Auth Module prerequisite)
Temple data creation and editing (Temple Authority Module)
Employee and contractor management (Temple Authority Module)
Document upload (Temple Authority only)
User management administration (Super Admin Module)
Audit log viewing (Super Admin Module)
Notification delivery via email and SMS channels (Notification Dispatch Module, separate poller/worker)
Scheduled jobs: overdue flagging, reminder emails, search summary reconciliation batch
AES-256-GCM encryption infrastructure (shared infrastructure prerequisite that must exist before DC module starts)
Geo master data seeding and management (Super Admin scope)

⚠️ FUTURE ROLE NOTE (P2-7 — State Government / Audit Bodies viewer role): The original requirements (Section 2.1 of temple_registry_requirements.txt) list State Government officials and Audit Bodies as stakeholders with read-only access to reports and public disclosures. This role (tentatively AUDITOR or STATE_VIEWER) is NOT implemented in v1 of the DC module. This is an accepted deferral. A dedicated viewer module or a future API v2 extension will introduce this role. Until then, audit bodies receive exported reports via the DISTRICT_COLLECTOR export function outside the portal.

SECTION 2: CORE ARCHITECTURAL DECISIONS
2.1 PRIMARY KEY STRATEGY

DECISION: All database entity tables use BIGINT AUTO_INCREMENT as the primary key. Entity classes map this as Long id in Java. The database generates primary keys via the MySQL AUTO_INCREMENT mechanism. The application NEVER generates PKs; @GeneratedValue(strategy = GenerationType.IDENTITY) is the exclusive PK generation strategy on all entity classes.

Rationale for BIGINT over UUID/CHAR(36):
  - Joins are faster (integer comparison vs string comparison)
  - Index size is smaller (8 bytes vs 36 bytes per FK reference)
  - No external UUID library or @PrePersist hook required
  - Fully deterministic ordering: id reflects insertion order
  - Simpler to read in audit logs, support queries, and manual DB inspection
  - Compatible with government data center databases that may not support UUID functions

BaseEntity carries: id (Long, BIGINT AUTO_INCREMENT), isDeleted (Boolean default false), createdAt (LocalDateTime), updatedAt (LocalDateTime), createdBy (Long, BIGINT FK to users.id), updatedBy (Long, BIGINT FK to users.id). The id field is the sole basis for equals() and hashCode() on all entity subclasses. No @PrePersist hook is needed; id assignment is handled by the database.

All FK columns in every table are BIGINT NOT NULL (or BIGINT NULL for optional FKs) to match. The acknowledgement_sequences table (Section 4.12a) also uses BIGINT AUTO_INCREMENT for its seq_id counter column; this is consistent with the general BIGINT strategy.

⚠️ JAVA ENTITY FIELD TYPE: All entity id fields are declared as Long id (not long — use the boxed type to allow null detection before persistence). All FK fields are declared as Long fkName (nullable FKs) or Long fkName @Column(nullable=false) (mandatory FKs). JPA @JoinColumn maps to the BIGINT FK column.

⚠️ IMPLEMENTATION NOTE (F11 — lock_version naming): The JPA @Version optimistic locking column on asset_declarations MUST be named lock_version in DDL and lockVersion in Java. This avoids collision with version_number (the business submission counter). Entity annotation: @Version @Column(name = "lock_version") private int lockVersion; DDL: lock_version TINYINT UNSIGNED DEFAULT 0. The field name "version" is forbidden on this entity for this reason.

🔗 CROSS-MODULE INTEGRATION CONTRACT (P1-4 — lock_version alignment): Both the DC module and the Temple Authority module MUST use the identical DDL column name lock_version on the asset_declarations table. If the TA module uses a different column name (e.g., "version" or "optimistic_lock"), Hibernate will fail to load the entity from the shared table with a mapping error. The canonical DDL definition lives in Flyway V8 under DC module schema ownership. The TA module MUST NOT redefine this column; it references the same V8 migration. This cross-module contract must be verified in a shared integration test that loads the AssetDeclaration entity from both module application contexts and asserts that the @Version field resolves to lock_version.

2.2 SOFT DELETE STRATEGY

Two patterns coexist in this codebase.

Pattern A (standard entities): Uses an is_deleted BOOLEAN column, default false. Applies to: temples, temple_profile_staging, trust_registrations, trust_board_members, asset_declarations, notification_events, in_app_notifications, and all geo entities. JPA filter annotation @SQLRestriction("is_deleted = false") is placed on the entity class. JPA delete override @SQLDelete issues an UPDATE SET is_deleted=true WHERE id=?. When a parent entity is soft-deleted, all children in the same aggregate are soft-deleted within the same transaction.

Pattern B (people entities): Uses deleted_at (DATETIME nullable) and deleted_by (BIGINT FK nullable). Applies exclusively to employees and contractors. JPA filter annotation @SQLRestriction("deleted_at IS NULL") is placed on the entity class. JPA delete override @SQLDelete issues UPDATE SET deleted_at=NOW(6), deleted_by=? WHERE id=?. These entities retain full history in place when soft-deleted.

⚠️ CONSTRAINT NOTE (F13 — employees CHECK constraint): Flyway V15 must add: ALTER TABLE employees ADD CONSTRAINT chk_emp_dates CHECK (date_of_leaving IS NULL OR date_of_leaving >= date_of_joining). This prevents corrupt data where a leaving date precedes the joining date. Enforcement is at the database level, not only application layer.

2.3 ENCRYPTION HANDLING

The AesEncryptionConverter is a REQUIRED infrastructure prerequisite. No entity annotated with @Convert(converter = AesEncryptionConverter.class) can be loaded by JPA without it. It must be fully implemented before any DC module entity class is compiled and loaded.

AesEncryptionConverter specification:

Algorithm: AES-256-GCM
Key source: environment variable TRM_AES_KEY (32-byte base64-encoded string)
IV: randomly generated per encryption, prepended to ciphertext before storage
Failure behavior: if the key environment variable is absent or invalid length at startup, the application MUST fail to start immediately. Never silently fall back to plaintext storage or decryption.
Encrypted fields and their display masking rules for API responses:

trust_registrations.pan_number_encrypted: shown as AB*****1Z for DISTRICT_COLLECTOR and DC_STAFF; full PAN shown only for SUPER_ADMIN
trust_board_members.pan_number_encrypted: shown as XXXXX9999X for ALL roles including SUPER_ADMIN. Never returned unmasked to any caller
trust_board_members.aadhaar_encrypted: shown as XXXX-XXXX-1234 for all roles
trust_registrations.bank_account_number_encrypted: shown as **XXXXX1234 for all roles
employees.aadhaar_encrypted: shown as XXXX-XXXX-1234 for all roles
Masking is applied exclusively in MapStruct mappers via @AfterMapping methods that call PiiMaskingService. PiiMaskingService performs two operations: (a) applies the mask string to the decrypted value, and (b) inserts a row into audit_pii_access_events. Both steps happen within the same read transaction as the data retrieval. The raw ciphertext string NEVER appears in any response DTO field under any circumstances.

⚠️ CRITICAL IMPLEMENTATION NOTE (S5 — PiiMaskingService REQUIRES_NEW): PiiMaskingService.mask() MUST be annotated @Transactional(propagation = REQUIRES_NEW). The calling read services use @Transactional(readOnly = true), which marks the JDBC connection as read-only. Any INSERT under a read-only connection (the audit_pii_access_events write) throws a runtime exception. REQUIRES_NEW suspends the outer read-only transaction, opens a new writable connection for the audit INSERT, commits it, then resumes the outer context. Omitting REQUIRES_NEW causes production failures on every PII field access.

2.4 RBAC ENFORCEMENT STRATEGY

Layer 1 - Method-level authorization: @PreAuthorize annotations on every public method of every service interface. This requires @EnableMethodSecurity(prePostEnabled = true) to be present on the SecurityConfig class. SecurityConfig is an Auth Module prerequisite. If @EnableMethodSecurity is absent, all @PreAuthorize checks are silently ignored. A mandatory build-time integration test verifies that a DC_STAFF principal attempting to call approve() receives HTTP 403, catching this misconfiguration.

Layer 2 - District scope assertion: Every service method that loads a single entity by ID calls assertDistrictScope(entityId, currentUser) immediately after loading the entity. For SUPER_ADMIN principals, the check returns immediately without restriction. For DISTRICT_COLLECTOR and DC_STAFF principals, if the entity's district does not match the principal's districtId, DistrictScopeViolationException is thrown. The GlobalExceptionHandler maps DistrictScopeViolationException to HTTP 404 Not Found, deliberately and always. The 404 response prevents information leakage about entity existence in other districts. A 403 is never returned for district scope violations on single-entity access.

Layer 3 - Query-level district filter: For all list operations, the district constraint is injected directly into repository queries via a parameterized WHERE clause. SUPER_ADMIN principals receive a null districtId value; when districtId is null, the query omits the district WHERE clause entirely, returning all districts.

🔒 SECURITY HARDENING NOTES (RBAC):
(R1 — Cross-service RBAC bypass via direct call): ArchUnit test required: no service class may invoke a method on another service class that carries @PreAuthorize. Calling a @PreAuthorize-protected method from within another Spring bean bypasses the AOP proxy if the call is on the injected interface, but only works correctly if the target bean is injected and called via its interface. ExportService calls TempleSearchSummaryRepository directly (not DcTempleSearchService) for this exact reason — see Section 6.10.
(R2 — Interface injection): All Spring-injected collaborators must be declared as their interface type in constructors, never as *ServiceImpl. This ensures AOP proxies wrap every injected instance and @PreAuthorize, @Transactional, and @Async annotations take effect.
(R3 — @EnableMethodSecurity integration test requirement): The integration test verifying that DC_STAFF principal cannot call approve() MUST use @SpringBootTest (full application context). @WebMvcTest slices do NOT load @EnableMethodSecurity and give false-passing results — silently ignoring all @PreAuthorize annotations.
(R4 — Null districtId non-SA is always an error): If assertDistrictScope is called for a CurrentUser whose role is NOT SUPER_ADMIN and whose districtId is null, throw IllegalStateException (not NullPointerException, not DistrictScopeViolationException). Null districtId on a non-SA principal indicates a corrupted JWT or a programming error, never a valid bypass.

2.5 DISTRICT SCOPING LOGIC

The district_id is extracted from JWT claims by JwtAuthenticationFilter and placed in the CurrentUser principal object at request initialization. Any district_id value provided by the client in URL parameters or request body is silently overridden with the value from the JWT claims. There is no configuration that allows this override to be disabled.

District scope traversal path for temples:
temples.hobli_id -> geo_hoblis.taluk_id -> geo_taluks.district_id

This three-hop join must be executed as a SQL JOIN chain, never as nested IN subqueries. Nested IN subqueries cause full-table scans at 30,000+ temple scale and are explicitly forbidden.

For SUPER_ADMIN: districtId in JWT claims is null. The query omits the district JOIN constraint. All temples across all districts are returned.

🔒 SECURITY HARDENING NOTES (scope traversal):
(R5 — JWT trust dependency): The DC module fully trusts all claims in the issued JWT (role, districtId, userId). If the Auth Module issues an incorrect JWT, the DC module has no secondary verification layer. This is an accepted system-level trust boundary.
(R6 — assertDistrictScope argument is always the Temple entity): assertDistrictScope receives the fully-loaded Temple entity, never a raw districtId. It traverses temple.getHobli().getTaluk().getDistrict().getId() internally. Never accept a raw district ID string as the scope check argument — it would allow callers to pass an unverified ID and defeat the check.

⚠️ NULL-GUARD REQUIREMENT (P0-4 — assertDistrictScope three-hop traversal): Before traversing temple.getHobli().getTaluk().getDistrict().getId(), each hop MUST be null-checked. Specifically:
  if (temple.getHobli() == null) throw new EntityNotFoundException("Temple has no hobli assignment: " + temple.getId());
  if (temple.getHobli().getTaluk() == null) throw new EntityNotFoundException("Hobli has no taluk assignment: " + temple.getHobli().getId());
  if (temple.getHobli().getTaluk().getDistrict() == null) throw new EntityNotFoundException("Taluk has no district assignment: " + temple.getHobli().getTaluk().getId());
  Allowing any hop to return null would produce a NullPointerException that escalates to HTTP 500 instead of a meaningful error. If geo seed data is incomplete (e.g., a hobli row has a null taluk_id FK in the database), the null-guard converts the runtime failure to EntityNotFoundException → HTTP 404, and the error is surfaced as a data integrity alert rather than an uncaughtexception. The null-guard check is placed inside the assertDistrictScope() implementation, not in callers.
(R7 — Identical 404 response body for scope violations and not-found): The HTTP 404 JSON body is byte-for-byte identical for EntityNotFoundException and DistrictScopeViolationException. Fixed body: {"success":false,"message":"The requested resource was not found.","errorCode":null,"errors":null}. Never include entity name, entity ID, or district information in any 404 body.
(R8 — Timing oracle mitigation): GlobalExceptionHandler adds a random delay of 0–20 milliseconds before returning any HTTP 404. This prevents distinguishing "entity not found" from "entity out of district" via response time. Implemented via ThreadLocalRandom.current().nextLong(0, 20) with Thread.sleep in the 404 handler before response construction.

2.6 TEMPLE SEARCH SUMMARY SYNC STRATEGY

temple_search_summary is a denormalized persistent table with one row per temple. It stores precomputed counts and status fields for fast search and dashboard aggregation. It is not a database view; it is a regular table updated by application code.

Sync mechanism for DC workflow actions: After every successful workflow action (approve, reject, clarify, flag-physical-verification, approveProfile, rejectProfile), the service calls TempleSearchSummaryService.refresh(templeId) within the SAME @Transactional boundary as the workflow action. The refresh method executes a native UPDATE query that recomputes the summary row for the specific temple. If the refresh fails, the entire transaction rolls back, preventing inconsistency between the summary and the normalized tables.

Initial population: V14 Flyway migration creates the table structure. A one-time backfill script, executed as part of first deployment, populates existing rows. The DC module itself does not contain the backfill logic.

Scheduled updates: Overdue flagging, year-end processing, and periodic reconciliation updates to this table are the responsibility of the Scheduled Jobs Module (out of DC module scope). The DC module's synchronous within-transaction refresh handles all workflow-driven changes.

🔗 CROSS-MODULE INTEGRATION CONTRACT (P1-5 — Temple Authority module MUST trigger refresh on declaration submission): When the Temple Authority module transitions an asset declaration from DRAFT to PENDING_REVIEW (the submission action), the TA module MUST call TempleSearchSummaryService.refresh(templeId) within the same transaction as the status update. If this call is absent, the DC dashboard's pending_declarations count remains at 0 for the newly submitted declaration until the DC performs the first workflow action on it. The DC cannot discover the new submission via search or dashboard KPIs.

Failure scenario: TA module submits declaration without triggering refresh → DC dashboard shows 0 pending → DC is unaware of new submissions → silent SLA breach.

Mitigation if TA module fails to call refresh: The Scheduled Jobs Module's periodic reconciliation batch will eventually correct the summary. Maximum staleness window equals the reconciliation batch interval (configured externally, target ≤60 minutes).

Enforcement: The TA module's declaration submission service must declare TempleSearchSummaryService as a constructor-injected dependency and call refresh(templeId) as the last step in the submission transaction, with propagation=REQUIRED so it joins the TA module's existing transaction.

⚠️ KNOWN LIMITATION AND DATA NOTES:
(S9 — pending_declarations count scope): The pending_declarations field in temple_search_summary counts declarations with status IN ('PENDING_REVIEW', 'CLARIFICATION_REQUESTED', 'PHYSICAL_VERIFICATION_REQUESTED'). All three statuses represent declarations actively requiring DC attention. Counting only PENDING_REVIEW would significantly undercount actionable items.
(S18 — Summary staleness after temple transfers): If a temple's hobli is reassigned to a different district (out-of-scope inter-district transfer), district_id in temple_search_summary becomes stale until the next workflow action fires refresh(). The temple appears in the old district's summary until then. Document this limitation in ops runbooks; remediation requires a manual refresh after any geo-hierarchy reassignment.
(F10 — Out-of-scope scheduler integration risk): If the Scheduled Jobs Module sets is_overdue=1 on asset_declarations without invoking TempleSearchSummaryService.refresh(), overdue_declarations in the summary becomes stale. The Scheduled Jobs Module MUST call the refresh service after each overdue-flagging batch. This is a cross-module integration contract that must be enforced at design time.

2.7 ACKNOWLEDGEMENT NUMBER GENERATION

Format: TRM/ACK/{financial_year}/{zero-padded 6-digit declaration id}
Example: TRM/ACK/2025-26/000142

Generation: Although asset_declarations.id is now a BIGINT AUTO_INCREMENT (globally sequential), it is NOT used directly for the acknowledgement number because it reveals the total number of declarations across all years and districts. A dedicated acknowledgement_sequences table provides per-financial-year sequential numbering (see Section 4.12a). It has two columns: seq_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY and financial_year CHAR(7) NOT NULL. On every APPROVED transition, the service executes INSERT INTO acknowledgement_sequences (financial_year) VALUES (:year) and immediately reads LAST_INSERT_ID(). This value is zero-padded to 6 digits for the acknowledgement number. MySQL AUTO_INCREMENT assignment is atomic; concurrent approvals produce different seq_id values by construction. The UNIQUE constraint on acknowledgement_number in asset_declarations is the database-level safety net.

⚠️ IMPLEMENTATION NOTES:
(S2 — seq_id zero guard): After INSERT INTO acknowledgement_sequences ... and reading LAST_INSERT_ID(), AcknowledgementNumberGenerator MUST assert that the returned value is > 0. If LAST_INSERT_ID() returns 0 (possible if the INSERT silently failed or the MySQL session was reset), throw AcknowledgementNumberConflictException immediately. Never produce acknowledgement number TRM/ACK/.../000000.
(R9 — Sequential number disclosure): Sequential acknowledgement numbers reveal the cross-district approval rate to any observer comparing approval documents from different districts. This is an accepted disclosure — numbers appear on official government-issued documents and are not classified. Will not be remediated in v1.

2.8 NOTIFICATION RELIABILITY STRATEGY

Notifications are NOT published via Spring ApplicationEvent pub/sub. They are NOT dispatched via @TransactionalEventListener(AFTER_COMMIT). Those mechanisms risk silent event loss on pod restart between transaction commit and event dispatch.

DECISION: A notification_events row is INSERTED into the database as part of the same @Transactional write transaction that executes the workflow action. This is a regular JPA repository save operation on the NotificationEvent entity. If the transaction commits, the notification row is committed atomically with the status change. If the transaction rolls back, the notification row is rolled back with it. No event is silently lost.

ON-PREM CHANNEL RESTRICTION: In v1 of the on-prem deployment, the only active notification channel is IN_APP. Email and SMS delivery require external SMTP servers or telecom APIs that may not be available in every government data center. The notification_events.channels JSON column always stores ["IN_APP"] for all workflow-triggered notifications. email_status and sms_status tracking columns are retained in the schema for future extension but are not populated in v1.

The Notification Dispatch Service (out of DC module scope) polls notification_events for rows with status=PENDING and creates in_app_notifications rows. The DC module only produces the event row with correct template_key, template_params, channels=["IN_APP"], and priority. It never calls any email or SMS provider.

2.9 EXPORT ASYNC HANDLING

Synchronous path: row count is fewer than 500. Export executes in the HTTP request thread. The file (PDF or CSV) is written to the local filesystem under {TRM_EXPORT_BASE_DIR}/exports/{jobId}.{pdf|csv}. Response returns a jobId and a relative download path; the caller fetches the file via GET /api/v1/export/{jobId}/download which streams the file from disk through the backend with permission checks.

Asynchronous path: row count is 500 or more. Export is delegated to a bounded ThreadPoolTaskExecutor named exportExecutor. HTTP responds immediately with HTTP 202, a jobId, and status=ASYNC. When the async job completes, a notification_events row for template EXPORT_READY is inserted with a link_url pointing to GET /api/v1/export/{jobId}/download. The DC retrieves the link from their in-app notification inbox.

AsyncConfig is a Spring @Configuration class that defines the exportExecutor bean and carries @EnableAsync. exportExecutor parameters:

corePoolSize: 2
maxPoolSize: 5
queueCapacity: 10
threadNamePrefix: export-
rejectedExecutionHandler: AbortPolicy (returns HTTP 503 when queue is full; callers must retry)

⚠️ CRITICAL IMPLEMENTATION NOTES (export async safety):
(S10 — @Async self-invocation forbidden): The @Async export method MUST live on a separate Spring bean (AsyncExportBean), not on ExportServiceImpl itself. Calling this.doExportAsync() from ExportServiceImpl bypasses the AOP proxy and @Async has no effect — execution runs synchronously in the HTTP thread regardless of the annotation. Inject AsyncExportBean into ExportServiceImpl; call asyncExportBean.doExport(params).
(S11 — Export audit INSERT in REQUIRES_NEW): AuditExportEventService.logExport() is annotated @Transactional(propagation = REQUIRES_NEW). The audit row commits in its own short transaction BEFORE the async job is submitted. If the queue is full (ExportQueueFullException), the audit row is already committed. Every export attempt is recorded regardless of queue state.
(S16 — Export without audit is forbidden): If the audit_export_events INSERT fails (database error), abort the export and return HTTP 500. An export without an audit trail is never permitted.
(S17 — Export deduplication via 409): If the same actor with identical filter parameters has an active export job submitted within the last 5 minutes, return HTTP 409 Conflict with the existing jobId. Do not create duplicate export jobs.
(R10 — Export rate limit): Export endpoints are rate-limited to 5 requests per 10 minutes per authenticated user. Enforced via database-backed rate_request_log table (Section 4.12b). Returns HTTP 429 Too Many Requests with Retry-After header on breach.

2.10 API RESPONSE ENVELOPE

All endpoints in the DC module return responses in a consistent JSON envelope. The GlobalExceptionHandler (@RestControllerAdvice) is the sole producer of all error envelopes; controllers never construct error responses directly and never catch exceptions.

Success response (HTTP 200, 201, 202):
{ "success": true, "message": "string", "data": { ... } }

For paginated list endpoints, "data" is the pagination wrapper object (see Section 7.3 for field names) placed directly inside "data" without additional nesting.

Error response (HTTP 4xx and 5xx, excluding HTTP 400 validation errors):
{ "success": false, "message": "Human-readable error summary", "errorCode": "TRM-WF-001", "errors": null }

Validation error response (HTTP 400 MethodArgumentNotValidException only):
{ "success": false, "message": "Validation failed", "errorCode": null, "errors": [ { "field": "remarks", "rejectedValue": "too short", "message": "Remarks must be at least 50 characters" } ] }

Rules:
- "errorCode" is present and non-null only for named domain exceptions per Section 5.5 (e.g. TRM-WF-001, TRM-DECL-010). It is null for HTTP 400 validation errors and for unhandled HTTP 500 errors.
- "errors" array is non-null and non-empty ONLY for HTTP 400 validation failure responses (MethodArgumentNotValidException). It is null for all other response types.
- The "message" field for a generic HTTP 500 error is always the fixed string: "An internal error occurred. Please try again later." The actual cause is logged server-side with the request_id (from X-Request-Id header or MDC) as the correlation key. Stack traces and SQL error detail are never written to the response body.
- FieldError.rejectedValue is included as a string in the validation error response. If the rejected value belongs to an encrypted field, GlobalExceptionHandler replaces it with the string REDACTED before serialization.
- No field in any response ever contains raw ciphertext, AES key material, full stack traces, internal class names, or SQL error detail.

SECTION 3: DOMAIN MODEL (CONCEPTUAL)
3.1 GEO HIERARCHY

Five read-only master data entities forming a strict parent-child hierarchy used for scoping all temple data to a district.

GeoState: Top-level administrative division. Fields: id, name, code.
GeoCity: Second-level division. Fields: id, stateId FK, name, code.
GeoDistrict: Third-level. The boundary unit for DC jurisdiction. Fields: id, cityId FK, name, code.
GeoTaluk: Fourth-level subdivision of a district. Fields: id, districtId FK, name, code.
GeoHobli: Lowest level. The geographic unit assigned to a temple. Fields: id, talukId FK, name, code.

DC users are assigned to exactly one GeoDistrict. Temples are assigned to exactly one GeoHobli. The path from temple to district is: temple.hobliId -> GeoHobli.talukId -> GeoTaluk.districtId.

3.2 TEMPLE CORE

Temple: The master registration record for a temple. Has one GeoHobli. The temple is the root aggregate owner for trust, employees, contractors, and declarations. Key identity fields: registrationNumber (unique), name, grade (A/B/C), status (ACTIVE/INACTIVE/SUSPENDED).

TempleProfileStaging: A versioned draft of temple profile details submitted by Temple Authority for DC review. Multiple staging rows may exist per temple, but at most one may be in PENDING_REVIEW status at any time. Carries its own status driving the profile workflow. Has version field (1-based, incremented on rejection and resubmission).

TempleProfileCurrent: The single currently-approved version of a temple's descriptive profile. At most one row per temple (unique constraint on temple_id). Replaced atomically when a new profile version is approved.

TempleProfileHistory: Immutable archive of previously approved profile versions. Append-only. One new row is written whenever an existing approved profile is superseded by a newly approved version.

3.3 TRUST

TrustRegistration: The legal trust entity governing the temple. At most one row per temple may have status=ACTIVE at any time. Contains PAN and bank account in encrypted columns. Directly saved by Temple Authority; no DC approval workflow in v1.

TrustBoardMember: An individual trustee linked to a trust. Has appointment and cessation dates. Multiple active board members per trust are permitted. Contains Aadhaar and PAN in encrypted columns.

TrustFinancial: Annual income, expenditure, and closing balance for a trust. Unique per (trustId, financialYear) pair.

TrustMeeting: Records of formal trust meetings. Multiple per trust. Has meeting_type ENUM (ANNUAL_GENERAL, EXTRAORDINARY, BOARD).

3.4 PEOPLE

Employee: A person employed by a temple. Has employee_type ENUM (ARCHAKA, ADMINISTRATIVE, ACCOUNTS, MAINTENANCE, SECURITY, OTHER) and employment_status ENUM (ACTIVE, ON_LEAVE, RETIRED, RESIGNED). Soft-deleted via deleted_at pattern (Pattern B). Historical records with RETIRED/RESIGNED status remain visible unless explicitly deleted.

EmployeeSuccession: Records the hereditary chain for ARCHAKA-type employees. Links a predecessor employee to a successor via a self-referential FK. Maximum depth of 10 in the chain.

Contractor: A company or individual contracted by a temple for specific work. Has contract_type ENUM and payment_status ENUM (PENDING, PARTIAL, COMPLETED, DISPUTED). Soft-deleted via deleted_at (Pattern B). Contains PAN in encrypted column.

3.5 ASSET DECLARATIONS

AssetDeclaration: The annual asset and financial declaration submitted by Temple Authority for a specific financial year. One declaration per (templeId, financialYear, versionNumber). The versionNumber increments when a rejected declaration is superseded by a new submission. Has @Version field for JPA optimistic locking. snapshot_json is frozen at transition to PENDING_REVIEW and never modified after.

DeclarationClarification: A single thread entry in a DC-Temple clarification exchange. Has direction ENUM (DC_TO_TEMPLE or TEMPLE_TO_DC) and a free-text section_name field. When direction is DC_TO_TEMPLE and section_name is PHYSICAL_VERIFICATION, the row serves as the physical verification findings record required before completing a physical verification workflow.

Asset sub-tables (8 total): Each is a child of AssetDeclaration linked by declaration_id FK.
Immovable assets: decl_immov_agri_land (agricultural land parcels), decl_immov_building (temple complex buildings), decl_immov_leased (leased properties), decl_immov_other (other land).
Movable assets: decl_mov_precious_metal (gold, silver items), decl_mov_artifact (idols, sacred artifacts), decl_mov_vehicle (vehicles), decl_mov_equipment (electronic and office equipment).
Financial instruments are stored as summary aggregate fields on the AssetDeclaration row itself (annual_income and annual_expenditure as DECIMAL(15,2)). Individual financial instruments (FDs, securities, bank balances) are NOT itemized in v1 sub-tables; only totals are captured. This is an accepted scope limitation — itemized financial asset tracking is deferred to a future version. Business justification: HR&CE Act compliance for v1 requires declaration totals only; itemized schedules are for audit-level review not yet in scope.

3.6 NOTIFICATIONS

NotificationEvent: An outbound delivery job row inserted by the application within the workflow transaction. Carries template_key (string identifying the message template), template_params (JSON snapshot of values at creation time), channels (JSON array; v1 on-prem: always ["IN_APP"]), priority, and retry tracking fields. Consumed by the Notification Dispatch Service (out of scope).

InAppNotification: The DC's in-app inbox record. Created by the Notification Dispatch Service after processing the NotificationEvent. Read by the DC module's NotificationQueryService. Has is_read flag and read_at timestamp.

3.7 SEARCH SUMMARY

TempleSearchSummary: One denormalized row per temple. Stores precomputed counts (pending_declarations, overdue_declarations, pending_profile_review) and denormalized geo identifiers (district_id, taluk_id, hobli_id) for fast WHERE filtering without joins to normalized geo tables. Used exclusively for read operations: search results and dashboard aggregation. Never used as input to workflow logic; normalized tables are always the source of truth for workflow.

3.8 OWNERSHIP BOUNDARIES

Temple Authority owns: temple creation, all staging submissions, employee and contractor management, declaration creation and submission, document upload.
District Collector owns: workflow action execution (approve/reject/clarify/flag), read-only access to all entities within their district, dashboard, export.
Super Admin owns: read access across all districts, force-draft override, user management, audit access.
System (schedulers) owns: overdue flagging updates to asset_declarations, search summary reconciliation.
DC Module owns in this specification: DC workflow, DC dashboard, DC search, DC export, notification inbox, and the /auth/me and geo read endpoints that the frontend depends on.

Document access control rules:
UPLOAD: TEMPLE_AUTHORITY only. Out of DC module scope per Section 1.3. The DC module contains no upload endpoint and no document mutation endpoints.
LIST DOCUMENTS / VIEW METADATA: DISTRICT_COLLECTOR, DC_STAFF, SUPER_ADMIN. District scope enforced via the associated entity's temple: for entity_type=TEMPLE use the temple's own district; for entity_type=DECLARATION use declaration.temple.hobli.taluk.district; for entity_type=TRUST use trust.temple.hobli.taluk.district; for entity_type=CONTRACTOR use contractor.temple.hobli.taluk.district. All four paths use the three-hop join with null-guards (see Section 2.5 P0-4 note). SUPER_ADMIN bypasses the district check. Every listing call inserts one document_access_log row (access_type=VIEW_METADATA) per document ID returned, within the same read transaction.
DOWNLOAD (local file streaming): DISTRICT_COLLECTOR and SUPER_ADMIN only. DC_STAFF receives HTTP 403. Backend streams the file from local filesystem using documents.file_path resolved against TRM_FILE_BASE_DIR. No presigned URLs. Every successful download generates a document_access_log row (access_type=DOWNLOAD) within the same transaction as the streaming initiation. Response headers: Content-Disposition: attachment; filename="{original_filename}", Content-Type: {mime_type}.
SOFT DELETE: TEMPLE_AUTHORITY only. No delete endpoint in the DC module.

DC module document endpoints:
GET /api/v1/temples/{templeId}/documents: returns all documents with entity_type=TEMPLE associated to the given temple. Logs VIEW_METADATA.
GET /api/v1/declarations/{declarationId}/documents: returns all documents with entity_type=DECLARATION. Logs VIEW_METADATA.
GET /api/v1/contractors/{contractorId}/documents: returns all documents with entity_type=CONTRACTOR associated to the given contractor. District scope enforced via contractor.templeId (three-hop join with null-guards). Authorization: DISTRICT_COLLECTOR, DC_STAFF, SUPER_ADMIN. Logs VIEW_METADATA. (P0-2 fix: required by REQ 3.4.2a for contractor PDF association.)
GET /api/v1/trusts/{trustId}/documents: returns all documents with entity_type=TRUST associated to the given trust. District scope enforced via trust.templeId (three-hop join). Authorization: DISTRICT_COLLECTOR, DC_STAFF, SUPER_ADMIN. Logs VIEW_METADATA. (P2-5 fix.)
GET /api/v1/documents/{id}/download: streams the document file directly from local filesystem. Backend resolves documents.file_path against TRM_FILE_BASE_DIR, validates path traversal (file_path must not contain .. or absolute segments), checks district scope, logs DOWNLOAD, then streams bytes to the HTTP response. DISTRICT_COLLECTOR and SUPER_ADMIN only; DC_STAFF receives HTTP 403. No presigned URLs, no expiry TTL — access is controlled per-request by Spring Security and district scope check.

⚠️ VALIDATION AND SECURITY NOTES (F14, R19):
(F14 — association_role must be a constant set, not free-form VARCHAR): document_associations.association_role is defined as VARCHAR(100) in DDL, but the service layer MUST validate it against a fixed constant set before insert: {OWNERSHIP_PROOF, AUDIT_REPORT, MEETING_MINUTES, PHYSICAL_VERIFICATION_EVIDENCE, GOVT_APPROVAL, DECLARATION_SUPPORT, IDENTITY_PROOF, OTHER}. Free-form strings violate the document categorization contract. Validate in the Temple Authority Module's document upload service (out of DC scope), but DC module DocumentQueryService may need to display and filter by these values.
(R19 — Orphaned document → 404): In DocumentQueryService.serveFile(), if no document_associations row exists for the given documentId (orphaned document with no entity linkage), throw EntityNotFoundException immediately — HTTP 404. Never stream a file for an orphaned document regardless of whether the documents row itself exists.
(N1 — Path traversal prevention on file serve): Before opening the file at documents.file_path, the service MUST resolve the full absolute path and verify it starts with TRM_FILE_BASE_DIR. Any path containing ".." or absolute segments is rejected with HTTP 400. This prevents directory traversal attacks on the local filesystem.

⚠️ FLYWAY ROLLBACK STRATEGY (P2-8): Flyway migrations are irreversible by design. MySQL DDL (ALTER TABLE, CREATE TABLE) is auto-committed and cannot be rolled back within a transaction. The only rollback path for a failed Flyway migration is a full database restore from the backup taken immediately before the migration.

Operational procedure:
  PRE-MIGRATION: Take a full logical dump (mysqldump --single-transaction) of the production database. Store it in a time-stamped location. Verify the dump is readable before applying the migration.
  ON MIGRATION FAILURE: Stop the application. Restore from the pre-migration backup. Fix the migration script. Re-run after verification in a staging environment.
  NEVER use flyway:repair to mark a failed migration as "resolved" without understanding the failure root cause — this leaves the database in an inconsistent state.
  V15 special risk: the ALTER TABLE on document_associations (ENUM extension) acquires a metadata lock. In MySQL 8.0+ this is an online operation (ALGORITHM=INPLACE) with no table rebuild, but verify on the specific MySQL version in use.

4.12b IDEMPOTENCY TABLE (Flyway V16) — replaces Redis-based idempotency cache

idempotency_records: id BIGINT AUTO_INCREMENT PRIMARY KEY, actor_user_id BIGINT NOT NULL (FK users.id), idempotency_key VARCHAR(255) NOT NULL (client-provided header value; max 255 chars; validated as non-blank before lookup), response_body MEDIUMTEXT NOT NULL (serialized JSON of the workflow response; stored on first successful execution), response_status SMALLINT UNSIGNED NOT NULL (HTTP status code of the first response; stored to replay the exact status), created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6), expires_at DATETIME(6) NOT NULL (created_at + 5 minutes; set at INSERT time).

Unique constraint: (actor_user_id, idempotency_key). Indexes: idx_idempotency_lookup ON (actor_user_id, idempotency_key), idx_idempotency_expiry ON (expires_at) (used by cleanup job to DELETE expired rows).

Workflow:
  1. Before executing any workflow action, IdempotencyService.check(userId, idempotencyKey): SELECT * FROM idempotency_records WHERE actor_user_id=? AND idempotency_key=? AND expires_at > NOW(6). If row found: deserialize response_body and return with response_status (skip workflow execution entirely).
  2. Execute workflow action. On success: IdempotencyService.record(userId, idempotencyKey, responseBody, statusCode): INSERT INTO idempotency_records (actor_user_id, idempotency_key, response_body, response_status, expires_at) VALUES (?, ?, ?, ?, NOW(6) + INTERVAL 5 MINUTE). If duplicate key (concurrent request with same key): ignore the conflict (ON DUPLICATE KEY UPDATE created_at=created_at; a no-op); return the first response.
  3. Scheduled cleanup job (every 15 minutes): DELETE FROM idempotency_records WHERE expires_at < NOW(6). Runs in a dedicated @Scheduled method in IdempotencyCleanupJob @Component, annotated @Scheduled(fixedDelay = 900000).

⚠️ TRANSACTION BOUNDARIES: IdempotencyService.record() runs in a SEPARATE transaction (propagation=REQUIRES_NEW) that commits the idempotency row AFTER the main workflow transaction commits. If the workflow transaction rolls back (e.g., audit failure), the idempotency row is NOT written. This ensures idempotency records are only created for successful outcomes.

4.12c RATE REQUEST LOG TABLE (Flyway V16) — replaces Redis/Bucket4j rate limiting

rate_request_log: id BIGINT AUTO_INCREMENT PRIMARY KEY, user_id BIGINT NOT NULL (FK users.id), endpoint_key VARCHAR(100) NOT NULL (e.g. 'export', 'doc_download', 'workflow'), window_start DATETIME(6) NOT NULL (truncated to 1-minute or 10-minute boundary depending on endpoint), request_count INT UNSIGNED NOT NULL DEFAULT 1, last_request_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6).

Rate limit enforcement at service/filter layer:
  For each incoming request, RateLimitService.check(userId, endpointKey, windowDuration, maxRequests):
    UPSERT into rate_request_log: INSERT INTO rate_request_log (user_id, endpoint_key, window_start, request_count, last_request_at) VALUES (?, ?, ?, 1, NOW(6)) ON DUPLICATE KEY UPDATE request_count = request_count + 1, last_request_at = NOW(6).
    SELECT request_count WHERE user_id=? AND endpoint_key=? AND window_start=? .
    If request_count > maxRequests: return false (caller returns HTTP 429). Else: return true.
  window_start is computed as: TIMESTAMP(DATE_FORMAT(NOW(6), window_format)) where window_format truncates to the window boundary (e.g., '%Y-%m-%d %H:%i:00' for 1-minute windows, '%Y-%m-%d %H:00:00' for 10-minute windows adjusted by bucket).
  Scheduled cleanup job (every 60 minutes): DELETE FROM rate_request_log WHERE window_start < NOW(6) - INTERVAL 1 HOUR.

Configured limits (applied at filter layer using RateLimitService):
  endpoint_key='export': maxRequests=5, windowDuration=10 minutes
  endpoint_key='doc_download': maxRequests=60, windowDuration=1 minute
  endpoint_key='workflow': maxRequests=30, windowDuration=1 minute

5.4 STATE TRANSITION VALIDATOR DESIGN

StateTransitionValidator is a Spring @Component holding an immutable Map constant initialized at class load time. Map key: a DeclarationStatus (or ProfileStatus) enum value. Map value: an unmodifiable Set of valid destination status values from that key.

Exposes one method: validate(from, to). If to is not in the valid set for from, throws InvalidStateTransitionException. Does not evaluate business guards. Business guards are evaluated by the calling service method after structural validation.

⚠️ IMPLEMENTATION NOTE (S3 — getOrDefault for terminal states): StateTransitionValidator.validate() MUST use map.getOrDefault(from, Collections.emptySet()) rather than map.get(from). Terminal states (APPROVED, REJECTED, SUPERSEDED) have NO outbound transitions and therefore NO entry in the map. Calling map.get(APPROVED) returns null, and calling null.contains(to) throws NullPointerException. getOrDefault(APPROVED, emptySet()).contains(anything) correctly returns false, throwing InvalidStateTransitionException as intended.
🧭 TESTING NOTE: State machine rejection matrix test — for every terminal state and every non-terminal state, verify the exact allowed and rejected transition set. Include transition from PHYSICAL_VERIFICATION_REQUESTED to CLARIFICATION_REQUESTED (forbidden; must throw TRM-WF-001).

SECTION 6: SERVICE LAYER DESIGN
6.1 SERVICE DESIGN PRINCIPLES

Every service has an interface and a separate *ServiceImpl class. All business logic lives exclusively in *ServiceImpl. Controllers contain zero business logic and zero try-catch blocks. @Transactional on every write method. @Transactional(readOnly = true) on every read method. @PreAuthorize on every public method of the service interface.

Cross-service calls within the DC module are made via the service interface, never directly to *ServiceImpl. When a helper method must participate in the same transaction (TempleSearchSummaryService.refresh, AuditService.logDataEvent, NotificationEventRepository.save), default propagation (REQUIRED) is used, meaning the helper joins the caller's transaction.

Logging: action name and entity ID only. Never log remarks text, PAN, Aadhaar, encrypted fields, or full payloads.

SECTION 7: SEARCH AND DASHBOARD DESIGN
7.1 SEARCH FILTER PARAMETERS

All filters are optional except the district boundary (enforced from JWT regardless of client input).

cityId: String. Filters temples within a specific city. Resolved against the denormalized city_id column in temple_search_summary. Used for cross-city filtering by SUPER_ADMIN, or refinement within a city for DC users. (P1-2 fix: requirements Section 3.1.1b mandates City/Town as a filter level.)
talukId: Long. Filters to a specific taluk within the DC's district.
hobliId: Long. Filters to a specific hobli.
grade: String. Comma-separated A, B, C. Absent means all grades.
keyword: String. Case-insensitive LIKE match on temple_name. Max 100 chars. Any user-supplied wildcard characters are escaped before use.
deityName: String. Case-insensitive LIKE on deity_name. Max 100 chars.
tradition: String. Exact ENUM match on religious_tradition.
trustStatus: String. Values: REGISTERED (maps to has_active_trust=1), UNREGISTERED (maps to has_active_trust=0). Absent means no trust filter. (P0-3 fix: requirements Section 3.1.3b mandates Trust Registration Status toggle as REGISTERED/UNREGISTERED.)
declarationStatus: String. PENDING maps to pending_declarations > 0. OVERDUE maps to overdue_declarations > 0. DECLARED maps to has_approved_declaration=1 (temple has at least one approved declaration; P2-1 fix — requirements Section 3.1.3c uses the term "Declared" for this state). REVIEWED maps to pending_declarations = 0 AND overdue_declarations = 0 AND has_approved_declaration=0 (completely reviewed with no outstanding). The previous REVIEWED mapping is deprecated in favor of this more accurate 4-value enum.
status: String. Default ACTIVE. Pass SUSPENDED or ALL to include other statuses.
establishedYearFrom: Integer. Inclusive lower bound.
establishedYearTo: Integer. Inclusive upper bound.
page: Integer. 0-based. Default 0.
size: Integer. Default 25. Maximum enforced at 100.
sort: String. Default: pending_declarations DESC, overdue_declarations DESC, last_declaration_at DESC NULLS LAST.

7.2 SEARCH QUERY STRATEGY

Executes entirely against temple_search_summary. No join to normalized temples table at search time. All geo identifiers use denormalized columns in the summary table.

District enforcement: WHERE s.district_id = :districtId. Omitted when districtId is null (SUPER_ADMIN).
City filter: AND s.city_id = :cityId. Applied when cityId is non-null. Uses denormalized city_id column in summary table. (P1-2 fix.)
Trust status filter: AND s.has_active_trust = 1 (for REGISTERED) or AND s.has_active_trust = 0 (for UNREGISTERED). Omitted when trustStatus is null. (P0-3 fix.)
Approved declaration filter: AND s.has_approved_declaration = 1. Applied when declarationStatus=DECLARED. (P2-1 fix.)
Active temple default filter: AND s.temple_status = 'ACTIVE'. Modified when caller passes status=ALL.
Keyword: LIKE CONCAT('%', :keyword, '%') against temple_name.
All filters applied with null-safe dynamic query construction (Criteria API or @Query with optional clauses).

The search NEVER joins back to temples, geo_hoblis, geo_taluks, or geo_districts.

7.3 SEARCH RESPONSE STRUCTURE

PaginatedTempleSearchResponse: data (list), totalElements (Long), totalPages (Integer), currentPage (Integer), pageSize (Integer), appliedFilters (echo of the resolved filter values for frontend URL reconstruction).

Each TempleSearchItemResponse: id, registrationNumber, name, grade, hobliName, talukName, districtName, pendingDeclarations, overdueDeclarations, pendingProfileReview, lastUpdate (most recent of last_declaration_at and last_profile_update_at as ISO-8601 datetime).

7.4 DASHBOARD AGGREGATION QUERY SHAPE

SELECT COUNT(*) AS totalTemples,
SUM(pending_declarations) AS totalPendingDeclarations,
SUM(overdue_declarations) AS totalOverdueDeclarations,
SUM(pending_profile_review) AS totalPendingProfiles,
SUM(CASE WHEN temple_grade = 'A' THEN 1 ELSE 0 END) AS gradeACount,
SUM(CASE WHEN temple_grade = 'B' THEN 1 ELSE 0 END) AS gradeBCount,
SUM(CASE WHEN temple_grade = 'C' THEN 1 ELSE 0 END) AS gradeCCount
FROM temple_search_summary
WHERE district_id = :districtId AND temple_status = 'ACTIVE'
(district_id condition omitted for SUPER_ADMIN)

7.5 DASHBOARD RESPONSE STRUCTURE

7.6 DATA FRESHNESS

8.4 DISTRICT REASSIGNMENT EDGE CASE

Auth Module performs this atomic operation on DC reassignment:
UPDATE users SET district_id = newDistrictId, token_revoked_before = NOW(6) WHERE id = userId
UPDATE refresh_tokens SET revoked_at = NOW(6) WHERE user_id = userId AND revoked_at IS NULL
INSERT audit_data_events

JwtAuthenticationFilter checks: if token.iat is before user.token_revoked_before, reject with HTTP 401. DC sees session expiry and is redirected to login. Maximum stale window: remaining TTL of the access token at time of reassignment. With 15-minute TTL, worst case is 15 minutes. Accepted trade-off.

In-flight request behavior: if a workflow action is in-flight when reassignment occurs, the transaction completes. District scope check already passed at request start with valid credentials. The reassignment takes effect for all subsequent requests. This is correct.

SECTION 9: NOTIFICATION AND AUDIT DESIGN
9.1 NOTIFICATION EVENT FLOW

Step 1: DC triggers a workflow action.
Step 2: Workflow service executes the operation within a @Transactional method.
Step 3: Within the same transaction, a NotificationEvent entity is constructed and persisted via NotificationEventRepository.save(). This is a standard JPA INSERT within the active transaction.
Step 4: Transaction commits. Both the status change and the notification_events row commit atomically.
Step 5: Notification Dispatch Service (out of DC module scope) polls notification_events WHERE status=PENDING ORDER BY priority ASC, and dispatches to in-app adapters only (IN_APP channel in v1 on-prem; email/SMS adapters are not wired in v1).
Step 6: On successful in-app dispatch, an InAppNotification row is created by the Dispatch Service. The DC reads these rows via NotificationQueryService.

Guarantee: notification_events row is committed within the workflow transaction. No event is ever silently lost due to pod restart or JVM crash.

9.2 NOTIFICATION TEMPLATE REGISTRY

DECLARATION_APPROVED: Recipient = temple's TEMPLE_AUTHORITY user. Channels: IN_APP. Priority: 3. Params: temple_name, financial_year, acknowledgement_number, declaration_id.
DECLARATION_REJECTED: Recipient = temple's TEMPLE_AUTHORITY. Channels: IN_APP. Priority: 4. Params: temple_name, financial_year, rejection_reason, declaration_id.
DECLARATION_CLARIFICATION_REQ: Recipient = temple's TEMPLE_AUTHORITY. Channels: IN_APP. Priority: 4. Params: temple_name, financial_year, clarification_remarks, declaration_id.
DECLARATION_PHYSICAL_VERIFICATION: Recipient = temple's TEMPLE_AUTHORITY. Channels: IN_APP. Priority: 4. Params: temple_name, financial_year, verification_notes, declaration_id.
DECLARATION_CLARIFICATION_REPLY: Recipient = DISTRICT_COLLECTOR for temple's district. Channel: IN_APP. Priority: 5. Params: temple_name, financial_year, declaration_id.
PROFILE_APPROVED: Recipient = temple's TEMPLE_AUTHORITY. Channels: IN_APP. Priority: 6. Params: temple_name, profile_version.
PROFILE_REJECTED: Recipient = temple's TEMPLE_AUTHORITY. Channels: IN_APP. Priority: 5. Params: temple_name, rejection_reason.

Recipient resolution and fallback: All recipient lookups are encapsulated in NotificationRecipientResolver, a Spring @Component called from within workflow services. All queries are performed within the same workflow transaction.

For TEMPLE_AUTHORITY recipient (templates: DECLARATION_APPROVED, DECLARATION_REJECTED, DECLARATION_CLARIFICATION_REQ, DECLARATION_PHYSICAL_VERIFICATION, PROFILE_APPROVED, PROFILE_REJECTED):
Query: SELECT id FROM users WHERE temple_id = :templeId AND role = TEMPLE_AUTHORITY AND is_active = 1 ORDER BY created_at ASC LIMIT 1.
If exactly one active user found: use that id as recipient_user_id on the NotificationEvent row.
If zero active users found: do NOT insert a notification_events row. The workflow action completes and commits successfully. Log exactly one WARN-level message: "No active TEMPLE_AUTHORITY user found for templeId={}; notification skipped." The log message must not contain the temple name, user data, or any PII field values.
If multiple active users exist (edge case in v1): use the one with the earliest created_at, as enforced by ORDER BY created_at ASC LIMIT 1. Exactly one notification row is produced.

For DISTRICT_COLLECTOR recipient (template: DECLARATION_CLARIFICATION_REPLY):
Query: SELECT id FROM users WHERE district_id = :districtId AND role = DISTRICT_COLLECTOR AND is_active = 1 ORDER BY created_at ASC LIMIT 1.
If found: use as recipient_user_id.
If not found: skip notification row, log WARN: "No active DISTRICT_COLLECTOR user found for districtId={}; notification skipped."

Fallback safety rule: Any unexpected database exception thrown inside NotificationRecipientResolver MUST be caught within that method and treated as the "skip + log WARN" path. The exception must NOT be re-thrown or propagated to the calling workflow service. Re-throwing would roll back the entire workflow transaction, including the status change on the declaration. Workflow state transitions are non-negotiable; notification delivery is best-effort.

⚠️ OBSERVABILITY NOTE (S14 — Metrics counter for skipped notifications): When NotificationRecipientResolver skips a notification (zero recipients found), in addition to logging WARN it MUST increment a metrics counter: Counter.builder("notifications.skipped.total").tag("template", templateKey).register(meterRegistry).increment(). A WARN log alone is insufficient for production — it will not trigger alerts or appear in dashboards. The counter enables alerting rules: if notifications.skipped.total > threshold in 5 minutes, page on-call.

9.3 AUDIT LOGGING RULES

Audit rows committed within the same transaction as the workflow action.

PII masking: before_value and after_value JSON have encrypted columns replaced with REDACTED_ENCRYPTED by AuditJsonSanitizer before insertion. Known PII field key patterns: keys ending in _encrypted, and keys named aadhaar, pan_number, bank_account_number.

Events audited:
Declaration APPROVED: 1 row. table=asset_declarations, operation=UPDATE.
Declaration REJECTED: 1 row. table=asset_declarations, operation=UPDATE.
Declaration CLARIFICATION_REQUESTED: 2 rows. asset_declarations UPDATE + declaration_clarifications INSERT.
Declaration PHYSICAL_VERIFICATION_REQUESTED: 2 rows. asset_declarations UPDATE + declaration_clarifications INSERT.
Profile APPROVED: 3 rows. temple_profile_staging UPDATE + temple_profile_current UPDATE (or INSERT) + temple_profile_history INSERT.
Profile REJECTED: 1 row. temple_profile_staging UPDATE.

IP address: extracted from HttpServletRequest X-Forwarded-For header (first IP in chain, validated max 45 chars) via a request-scoped bean populated by an OncePerRequestFilter.
Request ID: X-Request-Id header value; UUID generated and placed in MDC if absent.

SECTION 10: EXPORT SYSTEM DESIGN
10.1 DATA SOURCE

10.2 CONSISTENCY MODEL

Async export (500+ rows): point-in-time as of async thread execution, potential window of minutes.
All exports include "Data exported as of: {ISO-8601 timestamp of query execution}" in the report header.

10.3 ASYNC JOB LIFECYCLE

DC posts export request.
Audit_export_events row inserted (committed in short transaction before async submission).
Row count determined. If >= 500: ExportJobParameters submitted to exportExecutor.
HTTP 202 returned with jobId and status=ASYNC.
Async thread: streams rows via JDBC ResultSet iteration (never loads into List). Writes directly to {TRM_EXPORT_BASE_DIR}/exports/{jobId}.{pdf|csv}. No S3 upload; no external storage required.
On success: inserts notification_events (EXPORT_READY) with link_url=/api/v1/export/{jobId}/download. On failure: inserts notification_events (EXPORT_FAILED). The export file is not deleted on success (retained until manual purge or a scheduled cleanup job). Temp files used during generation are deleted in both cases.
DC retrieves the download via the in-app notifications panel. No email delivery of download links in v1.
If exportExecutor queue is full: HTTP 503 with Retry-After: 60.

10.4 FILE FORMAT SPECIFICATIONS

CSV: UTF-8 with BOM. Header row first. ISO-8601 dates. Plain decimal monetaries. Masked PII per Section 2.3. No raw encrypted values.
PDF: Government seal (placeholder), DC name, designation, district name, generation timestamp, total record count on cover. Tables in body. Page numbers in footer. Masked PII.

SECTION 12: KNOWN RISKS AND MITIGATIONS
12.1 CONCURRENCY RISKS

RISK: Simultaneous workflow actions on the same declaration.
MITIGATION: @Version on AssetDeclaration. Concurrent modification -> OptimisticLockException at flush time -> HTTP 409. Frontend shows: "Declaration was updated concurrently. Please refresh and try again." Frontend invalidates the declaration's RTK Query tag on 409.

🔁 CONCURRENCY IMPLEMENTATION NOTES:
(S20 — Catch ObjectOptimisticLockingFailureException, not OptimisticLockException): Spring Data wraps JPA's OptimisticLockException in ObjectOptimisticLockingFailureException before it reaches @RestControllerAdvice. The handler must catch the Spring wrapper class.
(Testing concurrency): Do NOT use Thread.sleep() to simulate concurrent access. Use CountDownLatch or Phaser: two threads both load the declaration, both hold the @Version value, first thread flushes and commits, second thread flushes and receives ObjectOptimisticLockingFailureException. Assert the second call returns HTTP 409.

RISK: Acknowledgement number collision.
MITIGATION: Number derived from declaration.id (already unique by PK). Same declaration cannot be concurrently approved twice because @Version prevents it. Different declarations have different IDs and thus different numbers. UNIQUE constraint on acknowledgement_number is the DB-level safety net.

RISK: clarification_round counter race condition.
MITIGATION: @Version on AssetDeclaration protects all fields including clarification_round as a unit. Two concurrent read-modify-writes result in one OptimisticLockException -> HTTP 409, not silent double-increment.

RISK: markAllRead UPDATE locks too many rows.
MITIGATION: LIMIT 200 per UPDATE call. Client calls repeatedly if needed.

12.2 PERFORMANCE RISKS

RISK: getTempleFullProfile N+1 queries.
MITIGATION: Exactly 5 targeted queries. Explicitly documented in Section 6.3. If a sixth query is introduced by mistake (lazy loading triggered in a loop), a test using Hibernate Statistics with a query assertion will catch it during development.

RISK: Temple search slow at 30,000+ temples.
MITIGATION: Executes against temple_search_summary only (indexed, denormalized). Max 100 rows per page. Composite indexes cover primary access patterns.

RISK: Dashboard aggregate query slow.
MITIGATION: Single aggregate SELECT on temple_search_summary with indexed district_id filter. Expected under 50ms at 30,000 rows.

RISK: Large async export OOMs the JVM.
MITIGATION: JDBC ResultSet streaming; never accumulates rows in a List. exportExecutor bounded at maxPoolSize=5, queueCapacity=10.

RISK: TempleSearchSummary refresh adds latency to workflow actions.
MITIGATION: Single native UPDATE by PK. Expected under 5ms. Acceptable trade-off for guaranteed synchronous consistency.

12.3 SECURITY RISKS

RISK: AES encryption key exposed or absent.
MITIGATION: Key from environment variable TRM_AES_KEY only. Application fails to start if absent or wrong length. Never logged. Production: sourced from secrets manager.

RISK: PAN and Aadhaar values leak into API responses via MapStruct auto-mapping.
MITIGATION: MapStruct mappers explicitly ignore raw encrypted fields in destination DTO. @AfterMapping hooks call PiiMaskingService to produce masked strings. Integration test validates that GET /api/v1/temples/{id}/profile response for DC role never contains a value matching full unmasked PAN pattern.

RISK: DC accesses out-of-district entities by guessing IDs.
MITIGATION: assertDistrictScope on all single-entity access. Returns HTTP 404 (not 403), removing existence signal for out-of-district entities.

RISK: @EnableMethodSecurity absent on SecurityConfig.
MITIGATION: Integration test: DC_STAFF principal calling approve() must return HTTP 403. This test fails if @EnableMethodSecurity is absent, blocking deployment.

RISK: CSRF on workflow mutation endpoints.
MITIGATION: Mutations use Authorization: Bearer header (access token in JS memory). Browser CSRF attacks cannot set this header. Refresh token uses HttpOnly cookie with SameSite=Strict. No CSRF token needed for DC module endpoints.

🔒 ADDITIONAL SECURITY RISKS AND MITIGATIONS:
(R1 — Cross-service @PreAuthorize bypass): RISK: A service calls another @PreAuthorize-protected service method directly on an injected implementation class, bypassing the AOP proxy. MITIGATION: ArchUnit test enforcing no *ServiceImpl class is referenced in any service constructor (only interfaces). Plus: ExportService calls repository directly, never DcTempleSearchService.
(R2 — Implementation injection escape): RISK: Developer injects *ServiceImpl instead of the interface, making AOP inapplicable. MITIGATION: ArchUnit test verifying all @Service class constructors declare only interface types as parameters.
(R5 — JWT claims trust): RISK: Compromised Auth Module issues incorrect JWT claims (wrong role, wrong districtId). MITIGATION: Documented accepted trust boundary. The DC module has no secondary JWT verification layer. Mitigation is Auth Module security, not DC Module.
(R7 + R8 — Timing oracle and identical 404 body): RISK: An attacker determines whether an entity exists in another district by comparing HTTP 404 response body or timing. MITIGATION: Fixed identical 404 body for both EntityNotFoundException and DistrictScopeViolationException. Random 0–20ms delay before returning any 404. See Section 2.5 notes.
(R9 — Sequential ack numbers): RISK: Sequential acknowledgement numbers reveal cross-district approval rate. MITIGATION: Accepted disclosure. Numbers appear on official government documents. Will not be remediated.
(R14 — Deep pagination exhaustion): RISK: page=999999 causes server to attempted to serve an empty page deep in a huge result set, consuming query resources. MITIGATION: Hard reject page > 10000 or page*size > 1,000,000 with HTTP 400 before query execution.
(R18 — Security headers): All API responses must include: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer. PII-bearing responses must include Cache-Control: no-store.

12.4 DATA CONSISTENCY RISKS

RISK: temple_search_summary row missing for a temple.
MITIGATION: TempleSearchSummaryService.refresh uses UPSERT semantics. Missing row is inserted on first workflow action. One-time backfill handles all pre-existing rows.

RISK: Notification template_params reference stale entity data.
MITIGATION: Params are snapshot values copied at notification creation time. Dispatch service uses stored params, not live entity queries.

RISK: Async export captures stale data.
MITIGATION: Documented limitation. "Data as of: {timestamp}" included in export header.

ASSUMPTION-1: Auth Module delivers @EnableMethodSecurity on SecurityConfig before DC module goes live. If absent, all @PreAuthorize checks are silently bypassed. The integration test (R3) catches this.

LIMITATION-1: temple_search_summary.district_id becomes stale after inter-district temple transfers (S18). No automated fix; requires manual refresh or a workflow action to trigger synchronization.
LIMITATION-2: Sequential acknowledgement numbers disclose cross-district approval volume (R9). Not remediated in v1.
LIMITATION-3: DC module does not validate JWT claims independently. Trust is delegated entirely to the Auth Module (R5).
LIMITATION-4: Async export data freshness: 500+ row exports may include data up to several minutes old depending on executor queue depth (Section 10.2). "Data as of" timestamp mitigates user confusion.

16.6 SECURITY NOTES FOR LOCAL FILE SERVING

Path traversal prevention is mandatory on every file serving endpoint:
  Path base = Paths.get(configuredBaseDir).toAbsolutePath().normalize();
  Path resolved = base.resolve(storedRelativePath).normalize();
  if (!resolved.startsWith(base)) throw EntityNotFoundException; // HTTP 404, not 400/500

Never expose path validation errors as 400 (discloses structure) or 500 (discloses internal error). Always return 404.
File paths stored in the database are RELATIVE to the configured base directory. Absolute paths must NOT be stored in the database.
Original filename from documents.original_filename is sanitized before use in Content-Disposition header: any double-quote characters stripped; value enclosed in double quotes.
