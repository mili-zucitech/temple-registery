1. PURPOSE

   Document the data elements, query strategy, and UX layout for the
   District Collector (and DC_STAFF) dashboard.

--------------------------------------------------------------------------------

3. DETAILED CONTENT

   3.1 DASHBOARD WIDGETS

   Widget                         | Data Source             | Refresh
   -------------------------------|-------------------------|------------------
   Total Temples in District      | temple_search_summary   | On login
   Pending Declarations           | temple_search_summary   | Every 5 min
   Overdue Declarations           | temple_search_summary   | Every 5 min
   Pending Profile Reviews        | temple_search_summary   | Every 5 min
   Recently Approved Declarations | asset_declarations      | On action
   Temple Grade Distribution      | temples (aggregate)     | Daily
   Recent Activity Feed           | in_app_notifications    | Real-time

   3.2 QUERY: DC DASHBOARD SUMMARY

   SELECT
     COUNT(*) AS total_temples,
     SUM(pending_declarations) AS total_pending_decl,
     SUM(overdue_declarations) AS total_overdue_decl,
     SUM(pending_profile_review) AS total_pending_profiles,
     SUM(CASE WHEN temple_grade = 'A' THEN 1 ELSE 0 END) AS grade_a_count,
     SUM(CASE WHEN temple_grade = 'B' THEN 1 ELSE 0 END) AS grade_b_count,
     SUM(CASE WHEN temple_grade = 'C' THEN 1 ELSE 0 END) AS grade_c_count
   FROM temple_search_summary
   WHERE district_id = :dc_district_id
   AND temple_status = 'ACTIVE';

   3.3 SEARCH RESULTS TABLE COLUMNS

   RESULT COUNT DISPLAY:
   Per requirements §3.1.1e, the search result count MUST be displayed prominently
   ABOVE the results list, before any record is rendered:
     "Temples found: {totalElements}" (e.g. "Temples found: 47")
   This is populated from the pagination wrapper in the API response:
     GET /api/temples response includes: { data: { content: [...], totalElements: 47, ... } }
   The frontend renders this count before the table component loads.
   On filter change, the count updates in-place (no full page navigation).
   If 0 results: display "No temples match your current filters." (not a 404).

   DYNAMIC SEARCH (no page reload):
   Filter changes must trigger React Query re-fetch, NOT full page navigation.
   Implementation: All active filters are stored as URL query params (useSearchParams).
   React Query's queryKey includes the filter object; any filter change invalidates
   the query and triggers background re-fetch with loading indicator on the results panel.
   The URL updates as filters change, supporting back-navigation and link sharing.

   Column               | Source                    | Sortable
   ---------------------|---------------------------|----------
   Temple Name          | temple_name               | Y
   Grade                | temple_grade              | Y
   Hobli                | hobli_name                | N
   Taluk                | taluk_name                | Y
   Pending Actions      | pending_declarations +    | Y (default sort)
                        | pending_profile_review    |
   Overdue              | overdue_declarations > 0  | Y
   Last Update          | last_declaration_at OR    | Y
                        | last_profile_update_at    |
   Actions              | View button               | N

   Default sort: pending_declarations DESC, overdue_declarations DESC,
                  last_declaration_at DESC

   3.4 FILTER PANEL

   - Grade: A / B / C (multi-select checkboxes)
   - Taluk: dropdown (filtered to DC's district)
   - Hobli: dropdown (filtered to selected Taluk)
   - Status: Active / Inactive / Suspended
   - Pending Only: checkbox (shows only temples with pending_declarations > 0)
   - Overdue Only: checkbox

   Filters persist in URL query params to support back-navigation.

   3.5 EXPORT

   - Export button: available for DC and DC_STAFF
   - Formats: PDF (official report) and CSV (data analysis)
   - Scope: current filtered view only (not all 30,000 temples)
   - Both formats include DC name, district, date on cover/header
   - Action logged in audit_export_events

--------------------------------------------------------------------------------

4. DECISIONS LOCKED

   - Dashboard data sourced from temple_search_summary (not real-time joins)
   - Pending actions sort is the default; DC cannot change default sort
   - Export scope limited to current filtered view for performance
